## 1. Architecture map

```
Telegram ──POST /api/telegram (apps/api/app/api/telegram/route.ts)
  │ 0. admitTelegramUpdate (services/telegramTransport.service.ts)
  │      secret header (timing-safe) → 401 on mismatch
  │      update_id insert into ProcessedTelegramUpdate (PK) → duplicate = 200, dropped
  │ 1. ensureLinkedChatRow, /start <token> linking (nova/telegram/telegram-link.ts)
  │ 2. persona === "nova" → handleNovaTelegramEvent (nova/telegram/telegram-turn.ts)
  │      production: Nova ignores updates without a valid TELEGRAM_WEBHOOK_SECRET
  ▼
handleNovaTelegramEvent
  ├─ who: MessengerUser → NovaAcademicProfile (+ NovaTelegramChannel)
  ├─ allowAction (NovaTelegramChannel.actionWindowStart/actionCount: taps+commands per minute)
  ├─ callback  → decodeCallback "p:<promptId>:<optionId>" → resolvePrompt (one conditional write)
  │              → runOptionAction (telegram-actions.ts) → product functions
  ├─ command   → showToday / offerStart / askOutcome / showStatus / showWeek / showProgress / showSettings
  └─ text      → turn lease (channel-store) → daily meter (spendAiRequest) + reserveForInteraction
                 → Understanding Brain → safeReading → decideAction (decision/action-decision.ts, pure)
                 → act() (same action functions) → runNovaOrchestrator (Response Brain words it)
  deliver(): one reply per update; a reply with options opens the learner's single open prompt
             (NovaTelegramPrompt, openKey unique) before sending; blocked → markUndeliverable

Scheduler: apps/api/lib/internal-checkin-scheduler.ts, setInterval 5 min, Render only
  runCheckinCron → runNovaProactiveCron (proactive/nova-proactive-cron.ts)
                     decideProactive (decision/proactive-decision.ts, pure: candidates → gates → rank)
                     proactive-outbox.ts: claim by (profileId, occurrenceKey) unique → ready → sending → sent|failed|unknown|abandoned
                 → runEventReminders (proactive/event-reminders.ts): NovaCalendarEvent.remindAt, same outbox, type event_reminder
  idle skip (services/schedulerIdle.ts): due moments from schedulerDueSources.ts
```

Data models: `NovaStudySession` (one open per learner, `openStudySession` under a row lock), `NovaDayFlow` (one row per learner per day, `items` Json of `FlowItem` with `at` "HH:MM" and `sessionId`), `NovaTelegramPrompt` (one open prompt per learner), `NovaTelegramChannel` (nudges on/off, "Not today" pause, undeliverable, lease, limits, daily model budget), `NovaProactiveMessage` (the outbox, both proactive messages and calendar reminders), `NovaCalendarEvent` (events with reminders and repeat rules), `UsageReservation`/`UsageLedger`/`UsageBalance` (Nova credits), `ProcessedTelegramUpdate` (dedup).

## 3. Known gaps, confirmed

1. **Later** acknowledges and schedules nothing (`runOptionAction` case `later`).
2. **Timed reminder in chat** returns "unavailable" by design (`decideAction` rule `reminder_unavailable`, documented in CLAUDE.md "A sentence never sets a reminder").
3. **Usage is cost-based**: a Telegram text turn reserves under `telegram_understanding` and settles at `ceil(measured cost / NOVA_CREDIT_MICROS)`, at least 1 (`billing/accounting/nova.ts settleInteraction`, `rules.ts creditsFor`). A turn with a reading and a wording can settle at 2 or more. It is also counted on the older daily meter (`spendAiRequest`).
4. **Plan-block start doesn't attach**: Telegram starts through `runNovaSessionCommand` directly, never `startFocus` (`product/day-flow.ts`), so the saved block never gets its `sessionId` and the web's "spent today" misses the time.

## 4. Reliability risks

| Risk | Today | Verdict |
|---|---|---|
| Duplicate updates / Telegram retries | `update_id` PK dedup before any pipeline; dedup failure processes anyway (logged) | OK |
| Double taps | Prompt resolution is one conditional write; second tap "closed"; `openStudySession` row lock means one session | OK (held by `nova-telegram.itest.ts`) |
| Stale buttons | Only the single open prompt is answerable; any older message's buttons are dead | Safe, but **too strict for plan notifications**: a newer reply (e.g. /status) kills the notification's buttons |
| Scheduler restart | Outbox states; stale `sending` → `unknown` (never resent); claims idempotent | OK |
| Timezone | Learner zone from profile (device-reported); no zone → no proactive message | OK; non-IST covered by tests |
| Quiet hours | 23:00–07:00 unless inside the chosen check-in window | OK for coaching; reminders the learner set ignore it (correct) |
| 2-a-day cap | Counts sent/unknown/sending proactive rows only; reminders excluded | OK |
| Blocked chats (403) | `markUndeliverable`, cleared on next inbound | Not shown on the web except the calendar page |
| 429 / retry_after | Classified, but the retry waits for the next 5-minute tick, max 3 attempts in 3 h | Acceptable for nudges; up to 5+ min late for a timed reminder |
| Webhook secret | Checked timing-safe; Nova ignores unsigned updates in production | OK; production registration not yet verified (Phase 4) |
| Delivery precision | 5-minute tick, idle-skip predicts only existing jobs | Timed plan notifications would be up to 5 min late |

## 5. Launch blockers, ranked

1. **Telegram's plan is not the learner's plan.** After applying a plan on the web, /today and Start on Telegram still show and start the engine's blocks and don't attach sessions to saved blocks. Fix before any plan notification (M1).
2. **Buttons with no outcome**: Later, and "remind me" in chat. A launch demo that taps Later shows nothing happening (M3, M7).
3. **No plan notifications at all** (M2, M5): the pitch's centrepiece does not exist yet; it needs a reminder/occurrence record (additive table) and delivery at a minute, not a 5-minute tick.
4. **Credits double-charged and cost-based** for one Telegram turn (M6): the daily meter plus the ledger, settling at 1–3 credits.
5. **No kill switches** for automatic sends other than `NOVA_PROACTIVE_DISABLED` (which also stops calendar reminders).
6. Copy: `/help` and `/start` don't say what Nova will and won't send (M9). Bot name still "Kevo AI Companion" (human step).

## Plan consequence

Nothing here changes the brief's plan, with two additions:
- **Plan-notification buttons get their own callback form**, `r:<occurrenceId>:<action>`, re-checked against the occurrence and the saved plan on every tap. They don't go through the single open prompt, which a later `/status` would close.
- **Personal reminders reuse `NovaCalendarEvent`** (repeat rules, outbox delivery and the calendar page already exist), so M7 adds no second reminder system.
