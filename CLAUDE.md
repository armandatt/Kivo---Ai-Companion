## Commands

Run from the repo root (`my-turborepo/`) unless noted.

```bash
# Development: all apps, or one
npm run dev
npx turbo dev --filter=web        # port 3000
npx turbo dev --filter=api        # port 3001

npm run build
npm run check-types               # use --force to bypass the turbo cache
npm run lint                      # only apps/web and packages/ui define a lint script
npm run format

# Tests (Jest, packages/api only; not wired into turbo)
npm test --workspace @repo/api
cd packages/api && npx jest --config jest.config.ts src/nova/__tests__/decision-graph.test.ts
cd packages/api && npx jest --config jest.config.ts -t "name of test"

# Prisma
npx prisma generate --schema packages/db/prisma/schema.prisma
(cd packages/db && npx prisma db push)   # must run from packages/db: its prisma.config.ts loads .env from the cwd

# Nova real-Postgres integration test (never point it at the app database)
cd packages/api && NOVA_TEST_DATABASE_URL=postgresql://... npm run test:integration

# One-off audit scripts
npx tsx --tsconfig tsconfig.json scripts/realityAudit.ts
```

- **Schema changes: always `prisma db push`, never `prisma migrate dev`.** The production database has drifted from `packages/db/prisma/migrations/`.
- Relative imports inside `packages/api/src/nova` are written without a `.js` suffix. Turbopack does not resolve `./x.js` to `x.ts`, and the API build fails if one is added.
- `apps/web/next.config.js` sets `typescript.ignoreBuildErrors: true`, so a passing `build` says nothing about types. `check-types` is the only type gate.
- Tests match `**/__tests__/**/*.test.ts`. `jest.config.ts` maps `@repo/db/client`, `../services/memory.service` and `../services/openai.service` to `packages/api/__mocks__/`, so tests never touch the database or OpenAI. The service mocks only apply to that exact relative specifier.
- Scripts in `scripts/` run against the real database from `DATABASE_URL`.

## Architecture

Turborepo monorepo (npm workspaces) for **Kivo**, an AI accountability companion delivered over Telegram, with a web app for onboarding and a dashboard.

- **`apps/api`**: Next.js used as an API-only server, deployed to Railway. Routes are under `app/api/`. `app/api/telegram/route.ts` is the core runtime loop.
- **`apps/web`**: Next.js marketing site, onboarding quiz and dashboard, deployed to Vercel.
- **`packages/api`** (`@repo/api`): all business logic, with no HTTP knowledge. Consumed through subpath exports (`@repo/api/services/*`, `@repo/api/engines/*`, `@repo/api/nova`, ...). A new top-level folder under `src/` needs an entry in the `exports` map of `packages/api/package.json`.
- **LLM calls** all go through one function, `generateOpenAIText` in `packages/api/src/services/openai.service.ts`. The name is historical: it calls Claude, Gemini or OpenAI depending on configuration (`services/llmProviders.ts`): Claude when `ANTHROPIC_API_KEY` (or `CLAUDE_API_KEY`) is set, else Gemini when `GEMINI_API_KEY` is, else OpenAI; `LLM_PROVIDER` (`anthropic`/`claude`, `gemini`, `openai`) forces one. Call sites pass OpenAI model names, which are treated as a tier (`*-mini` = fast, anything else = main), so never add a second client or call a provider directly. On Claude (official `@anthropic-ai/sdk`, streamed and collected whole) both tiers are `claude-haiku-5-5` at effort `low`, the owner's choice for cost and speed (`ANTHROPIC_MODEL_FAST`/`_MAIN`, `ANTHROPIC_EFFORT_FAST`/`_MAIN` override). **Price tier:** Haiku 5.5 costs five times as much for a prompt over 100,000 input tokens, so nothing over `CLAUDE_PROMPT_TOKENS_MAX` (100 000; `ANTHROPIC_PROMPT_TOKENS_MAX`) is sent: text is guessed at 3 characters a token, and a request with files or long text is counted first with the free `count_tokens`; one over the limit fails with `OVER_PRICE_TIER` (`isOverPriceTier`), never cut down, and the plan writers answer `FILES_TOO_BIG` (send fewer pages). Only files get near it (a PDF page is roughly 1,500 to 3,000 tokens); thinking is left adaptive, so `max_tokens` gets `CLAUDE_THINKING_HEADROOM` on top of the caller's cap; `json` adds a system line (Claude has no schema-less JSON mode) and unwraps a fence; Opus requests carry `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`) so a safety decline is re-run server-side, and a final `refusal` is an error. Held by `llm-claude.test.ts`.
- **`packages/db`** (`@repo/db/client`): Prisma client using `@prisma/adapter-pg`. Schema at `packages/db/prisma/schema.prisma`; `prisma.config.ts` prefers `DIRECT_URL` over `DATABASE_URL`.
- **`packages/ui`**: minimal shared React stubs.
- **`apps/extension`**: the Nova browser extension (Manifest V3, plain ES modules, no dependencies). `npm run build --workspace nova-extension` writes `dist/`; `npm test --workspace nova-extension` runs its tests. See its `README.md`.

### Web to API

`apps/web` owns only the auth POSTs (`/api/login`, `/api/signup`, `/api/signup/verify`, `/api/signup/resend`, `/api/forgot-password`, `/api/reset-password`, all through `app/api/auth-proxy.ts`, which also signs the session cookie on the web side) and a few local handlers. Every other `/api/*` call is proxied to `apps/api` by the `rewrites()` list in `apps/web/next.config.js` (target `API_URL`, default `http://localhost:3001`). **A new API route that the web app calls needs a rewrite entry there**, or it returns 404 from the web origin.

Auth is a JWT cookie named `kevo_session`, verified with `jose`. `apps/web/middleware.ts` guards the protected routes; `apps/api/lib/auth/session.ts` creates and verifies sessions. Email/password and Google OAuth are both supported.

### Authentication

The rules live in `packages/api/src/auth/` and are tested there: unit tests against an in-memory fake, and `__integration__/auth.itest.ts` against real Postgres (the only proof of the concurrency guarantees). The route files in `apps/api` are one line each: `lib/auth/auth-route.ts` calls `handleAuthRequest` (`auth/http.ts`) and sets the cookie. Each service takes its database, hasher and mailer as `AuthDeps`.

- **Every auth POST from the browser goes through `apps/web/app/api/auth-proxy.ts`**, as a local route handler, never a rewrite. The proxy refuses cross-site requests and tells the API which browser is asking. A new auth POST needs a handler there. It always answers JSON: a missing or non-http(s) `API_URL` or a missing `JWT_SECRET` is a 503, an unreachable API a 502, a slow one a 504 (`UPSTREAM_TIMEOUT_MS`), and a reply that is not the API's (a host's error page, Railway's "Application not found") a 502 logged as "check API_URL". The browser gets one generic sentence; the log names the kind of failure only. In production `API_URL` has no default.
- **Cross-site requests are refused** (`request-origin.ts`, applied by the proxy and again by the API): `Content-Type` must be `application/json`, an `Origin` header must be the app's own, and `Sec-Fetch-Site` must not say another site. A request with no `Origin` is not from a browser page and is let through to the limits.
- **Email signup is two requests.** `POST /api/signup` stores a `PendingSignup` (password already hashed, the eight-digit code as an HMAC keyed with `JWT_SECRET`), emails the code and returns a random `signupToken`. `POST /api/signup/verify` needs the token and the code, and only then creates the `User` and grants the session. No `User` row exists before that. Signup accepts any address `isValidSignupEmail` allows (`email-rules.ts`: no IP literals, quoted parts or single-label domains); login, reset and Google use the looser `normalizeEmail`, so every address an existing account was made with still works. `isGmailAddress` remains only for Google's account-linking rule.
- **A signup belongs to the browser that started it.** Each start is its own row, reached only by its token (stored as SHA-256). A second start for the same address makes a second row and cannot change, resend or verify the first. Never go back to one row per address updated in place: that let a second caller put their password on someone else's signup.
- **A failed send leaves nothing unusable.** When the code email is not accepted, `startSignup` deletes the row it made (the browser never gets its token) and `resendSignupCode` puts the previous code and expiry back, so a code still on its way keeps working. The address's sends are still used up: the limits count emails asked for, not delivered.
- **Wrong codes are counted per attempt, across resends** (`PendingSignup.attempts`, never reset), and the count is taken with a guarded write before the code is compared. A resend without the attempt's token sends nothing and uses none of the address's sends.
- **Single use comes from guarded writes**, not from reading first: the code is consumed by a `deleteMany` on `(id, codeHash)`, a reset token by an `updateMany` on `used: false`.
- **Limits that protect an account are per address and in Postgres** (`throttle.ts`, table `AuthThrottle`, keys hashed): sign-in tries (10 per 15 minutes, taken before the password is checked, given back on success or a completed reset), signup emails (one a minute, 5 an hour, 10 a day) and reset requests (3 an hour). They are pauses that end by themselves, never locks.
- **Limits per caller are in memory and secondary** (`rate-limiter.ts`, `createCallerLimits`). The API believes a browser address only when the request carries the web proxy's proof (`proxyProof`, derived from `JWT_SECRET`). `X-Forwarded-For` is never read. Callers without the proof share one allowance per route.
- **Nothing says whether an address has an account.** Signup, resend and forgot-password give the same reply either way and tell the owner by email instead (including "this account signs in with Google"); an address with an account goes through the same steps as a new one. Login has one refusal and always compares a hash. Keep it that way when adding a branch.
- **Login is not gated on `emailVerified`.** Accounts created before verification existed have it null and still sign in.
- **Google** uses the authorization-code flow with `state` and a nonce in the `kevo_oauth` cookie. `lib/auth/google-oidc.ts` verifies the ID token with `jose` (signature, issuer, audience, expiry); `google-signin.service.ts` then decides the account. An account is recognised by Google's `sub` first. A matching email links only when Google is authoritative for the address (`email_verified` and either `@gmail.com` or an `hd` claim naming the address's own domain) and the Kivo account has no password or a verified email. Otherwise nothing is linked: `/signin?error=google_link` (reset the password first, which sets `emailVerified`) or `google_manual` (sign in with the password). Google's tokens are not stored.
- **Reset tokens are stored as SHA-256** in `PasswordResetToken.token`. The link carries the only copy.
- **`JWT_SECRET` has no default in production.** The session code (`apps/api/lib/auth/session.ts`, `apps/web/lib/auth/session-secret.ts`) and `serverSecret()` throw when it is missing; the development fallback applies only outside production.
- **Sessions cannot be revoked.** A password reset does not end sessions issued before it; they last until the 30-day JWT expires.
- Auth mail goes through `auth-email.ts` (Resend). Codes, tokens, passwords and recipient addresses are never logged, and an unexpected error is logged by name only.
- `RESEND_API_BASE` points mail at another host. It is for an end-to-end harness's local stand-in (like `TELEGRAM_API_BASE`), so a test reads the real code from the captured message. Never set it in a deployed environment.
- `scripts/e2e/fresh-user.mjs` signs up the real way: its stand-in on port 3999 serves as the email provider too (`servers.sh` sets `RESEND_API_BASE`), and the script reads the code from the captured message and verifies it with its `signupToken`. Its `sql` helper calls `docker exec nova-test-pg psql`.

### Telegram webhook: an ordered chain of gates

`POST /api/telegram` is a long sequence of early returns. Order is the behaviour, so read the surrounding gates before inserting one.

0. **Transport safety** (`services/telegramTransport.service.ts`): secret-token check, then `update_id` dedup in Postgres (`ProcessedTelegramUpdate`). A replayed update returns 200 and reaches no pipeline. Applies to every persona.
1. Profile update, then `/start <token>` handling (links a web account to a chat).
2. **Persona branch.** If `MessengerUser.persona === "nova"`, the update goes to `handleNovaTelegramEvent` (`packages/api/src/nova/telegram/telegram-turn.ts`) and nothing below runs. Button taps (`callback_query`) are routed to the same handler before step 1, because only Nova has buttons. Everything below is Rex. `/start <token>` linking for both companions is `nova/telegram/telegram-link.ts`.
3. **Intake / onboarding.** `needsIntake()` routes to onboarding V3 (`ONBOARDING_V3_ENABLED=true`), else V2 (`isV2Active()`), else the V1 `intake.service` for legacy users. Then the post-onboarding activation flow.
4. **Slash commands**: `/log`, `/pr`, `/progress`, `/history`, `/overload`, `/streak`, `/split` (`workoutTracking.service`), `/reminders`, `/cancel N`. `/log` is first checked against the Reality Layer for an active illness or injury.
5. **Parsing Engine V2** (`engines/parsing-engine-v2.ts`) does structured extraction, while the **Understanding Layer** (`engines/understanding-layer.ts`, an LLM call) runs concurrently for semantic intent.
6. Rate limit, then a per-chat in-memory processing lock (45 s TTL).
7. Deterministic handlers: reminders, active workout logging, gym short-circuit, health events, entity extraction, focus sessions, deadlines, check-in scheduling, progress and weekly review, acknowledgements, off-topic, nutrition logging.
8. **Semantic Router** (`engines/semantic-router.ts`) arbitrates between the parser and the Understanding Layer. A conflict on a state-changing action asks the user for clarification instead of executing.
9. **Default path**: `runOrchestrator` in `engines/mentor-orchestrator.ts`.

The lock, the closure-reply dedup and the daily-warning set are process-level `Map`s. They are correct only because Railway runs a single persistent instance.

### Rex: the mentor orchestrator

`runOrchestrator` dispatches to `runOrchestratorV3` when `MENTOR_V3_ENABLED=true`; otherwise it runs the legacy V1 pipeline in the same file. V3 with the V5 cognitive layer is the live system. It loads memory, mentor state and patterns, builds one large system prompt (`buildRexSystemPrompt`), calls OpenAI for a JSON reply, validates it and persists state.

**Rule for Rex: OpenAI is the understanding and coaching brain.** It classifies intent, emotion and goals and picks the coaching approach. Deterministic code only verifies, calculates, constrains and persists. Improve Rex by giving the prompt better evidence or instructions, not by adding regex or keyword classifiers or new decision engines.

`processor/messageProcessor.ts`, `services/decision.engine.ts` and the `intent`/`emotion` services are the legacy V1 NLP layer. Do not extend them.

### Nova: the study companion

`packages/api/src/nova/` is a separate pipeline with the opposite rule: **code decides, the LLM expresses.** It is governed by `../SKILL.md` ("Nova's Constitution", one level above this repo), which the code cites by section. If code and that document disagree, the code is wrong.

`nova-orchestrator.ts` is the single entry point: study snapshot → Understanding Brain (`gpt-4o-mini`, classification only) → deterministic engines (signal, academic state, knowledge, pattern, exam, planning) → Decision Graph (`decision/`, selects the intervention) → context builder → Response Brain (`gpt-4o`, wording only) → fire-and-forget persistence. Nova has its own onboarding (`nova/onboarding/`), proactive messaging (`nova/proactive/`) and `Nova*` tables. It reaches shared Rex services only through `nova/adapters/`.

**Evidence is not memory (SKILL.md §11.7).** Signals, classifications and LLM output are evidence. Only `nova/consolidation/` may turn evidence into durable state: `consolidator.ts` holds the rules (pure, no DB, no LLM), `run-consolidation.ts` applies them, and each table has one store under `consolidation/stores/`. Nova never touches `MemoryFact`; its conversation log is `CompanionMessage`, via `adapters/conversation-adapter.ts`. A turn's consolidation is a retryable job in Postgres (`NovaConsolidationJob`) applied in one transaction. Regex signals are candidates only: `establishedSignals()` drops any the Understanding Brain does not corroborate, and session start comes from `/study` or the Understanding Brain's `sessionIntent`, never from a regex. The reality vocabulary is shared with Rex in `src/types/reality.types.ts`. `consolidation-boundary.test.ts` fails if a write bypasses this. See `docs/NOVA_CONSOLIDATION_ARCHITECTURE.md`.

### Personality signal and mentor matching

`packages/api/src/personality/` is deterministic and never calls the LLM. Accounts onboarded before 20 October answered four statements (verbatim public-domain IPIP items). They produce a **personality signal** (`kivo-signal-v1`), not a Big Five assessment: one item per dimension is not a validated scale, so never present it as a measured trait, to the user or to the model. New accounts answer the **coaching preferences** instead (`kivo-style-v2`, below); the newest `PersonalityAssessment` row of either kind is the current one.

- `signal-items.ts` / `signal-scoring.ts`: the statements, validation, reverse-scoring, 0 to 100 scores, low/mid/high bands, and the behavioural lines that are the only form the signal takes in a prompt.
- `mentor-registry.ts`: matching metadata for the personas in `personna.service.ts` (assignable, domains, characteristics). The numbers are a product hypothesis. Only `rex`, `nova` and `zen` are assignable.
- `mentor-compatibility.ts`: `matchMentor`. Domain filtering decides eligibility and is a hard constraint, because a persona selects a whole pipeline; compatibility scoring only ranks eligible mentors. The accountability answer sets intensity outright and the signal may only nudge other dimensions. Each domain has one eligible mentor today (gym → rex, study → nova, general → zen), so the score is recorded but does not yet change the outcome.
- `personality.service.ts`: persistence. Raw answers and the derived signal live in `PersonalityAssessment` (one row per run); how the mentor was chosen lives in `UserProfile.mentorMatch`; the assignment stays in `UserProfile.primaryPersona`. A re-run (`POST /api/personality`) never changes the assigned mentor.

`UserProfile.mentorMatch.resolution` says how the assignment came about, and `match` is only ever stored when it names the mentor actually assigned:

| `resolution` | Meaning | `match` |
|---|---|---|
| `engine` | The user gave a domain and the engine chose | The engine's match |
| `domain_missing_default` | No domain was given, so the general default (`zen`) was assigned | The engine's match |
| `legacy_client_persona` | An older client sent no domain but named the persona itself, which is still honoured | `null` |
| `predates_matching` | The user was assigned before this feature; set the first time they re-run the statements | `null` |

`mentorMatch.reassessment` holds the newest re-run. Its `match` is `null` when the profile has no domain to match against. `mentorMatch` is internal: `POST /api/onboarding` strips it from the profile it returns.

`POST /api/onboarding` runs the engine server-side; the browser shows no persona reveal. The v1 signal reaches prompts as at most three behavioural lines, in Rex's profile block (`buildRexSystemPrompt`) and Nova's dynamic layer (via `nova/adapters/operating-style-adapter.ts`), and only when `PERSONALITY_SIGNAL_ENABLED=true`. Stated v2 preferences reach Nova's prompts without the flag (`getCoachingStyleForChat`), under their own header; Rex reads only v1. The lines say how to deliver coaching (structure, sequencing, reasoning, kind of question) and never how hard or gently to push: intensity is the user's explicit accountability choice.

**Deployment order.** Prisma reads every column of a model unless a query has its own `select`, so the new code fails on a database that lacks `UserProfile.mentorMatch` (onboarding, the Telegram `/start` link and settings updates all break).

1. Apply the schema to the target database first: `(cd packages/db && npx prisma db push)`. The change is additive, so the code already running keeps working.
2. Then deploy the application code.
3. Leave `PERSONALITY_SIGNAL_ENABLED` unset until the deployed application and database are verified and real replies have been checked with it on.

Known gaps, deliberately not fixed here: `UserProfile.primaryPersona` is never copied to `MessengerUser.persona` (nothing writes that field, so web-onboarded users stay on the default `rex` on Telegram), and the Rex V3 prompt is hard-coded to Rex's voice whatever the persona.

### Proactive messaging

`runCheckinCron` in `apps/api/lib/checkin-cron.ts` sends dynamic check-ins, custom reminders, gym cues and Nova proactive messages; each job has its own `try`, so one failing does not stop the others. It is driven by an in-process 5-minute `setInterval` started from `apps/api/instrumentation.ts` (disable with `DISABLE_INTERNAL_CHECKIN_CRON=true`). `render.yaml` sets that flag to `false`: Render is the one host that runs it. `GET /api/health` reports `scheduler.state` (`running` / `disabled`) with the time and result of the last tick. `GET /api/checkin` runs one tick by hand; nothing deployed calls it, and it requires `Authorization: Bearer $CRON_SECRET` (closed in production when `CRON_SECRET` is unset). The root `vercel.json` still declares a cron for `/api/checkin`, but the web app has neither that route nor a rewrite for it. Nova's part is described under "Nova on Telegram".

### Data model

Two user identities, deliberately not merged:

- **`User`**: web account, with `UserProfile` (quiz results, gym settings) and the gym tables (`WorkoutLog`, `LiftLog`, `SorenessLog`, `BodyweightLog`, `EnergyLog`, `InjuryFlag`).
- **`MessengerUser`**: Telegram identity keyed by `(platform, platformChatId)`. Owns conversation memory (`CompanionMessage`, `MemoryFact`), goals, deadlines, focus sessions, Telegram workout logging, `UserReality` and all `Nova*` tables.

`MemoryFact` is also Rex's generic state store: onboarding V2 state, active investigations and mentor state history are rows distinguished by `type`/`key`. `UserReality` (the Reality Layer: current illness, injury, travel and similar temporary facts) is kept separate from memory.

Personas are defined in `services/personna.service.ts` (the misspelling is the real filename). The active one is `MessengerUser.persona`.

All are read from `process.env` at call time, so flipping one on Railway needs no deploy.

## Deployment

- **Render** (`render.yaml`, steps in `RENDER_DEPLOYMENT.md`) is the target host for `apps/api`: one always-on web service, one instance, health check `/api/health`. The 5-minute scheduler runs inside that process, so there is no Render Cron Job or worker; adding one would run every job twice. `DISABLE_INTERNAL_CHECKIN_CRON=true` turns the scheduler off on a host.
- **Railway** (`railway.json`, `RAILWAY_DEPLOYMENT.md`) is the previous host, kept until Render is verified. Only one of the two may run the scheduler or receive the Telegram webhook at a time.
- **Vercel**: Root Directory `apps/web`; `apps/web/vercel.json` runs `prisma generate` before the build.
- `prisma generate` is not a `postinstall` step. Run it by hand after a fresh install or a schema change.

## Who a Nova learner is

One learner per person, with or without Telegram. `nova/product/learner-identity.ts` (`resolveLearnerForAccount`) is the only place an account becomes a learner; `apps/api/lib/nova/resolve-learner.ts` supplies the account from the session cookie and nothing from the request.

- A learner is a `NovaAcademicProfile` on a `MessengerUser` row, named by one string that every product function takes as `platformChatId`: a Telegram chat id, or `web:<userId>` for a Nova account with no chat (`nova/product/learner-key.ts`, pure). Look a learner up with `learnerKey(id)`; never write `platform: "telegram"` into a Nova lookup (`lifecycle-hardening.test.ts` reads the source to hold this).
- The web row is made on the account's first request, only when `primaryPersona` is `nova`, and the unique key makes that idempotent.
- **Connecting Telegram re-keys the row** (`nova/telegram/telegram-link.ts`, one transaction): the same row id, profile and history, now found by the chat id. The placeholder row the webhook made for that chat is set aside (`platform: "telegram_replaced"`), not deleted. A chat that already has a Nova learner (`chat_has_learner`) or a finished Rex setup (`chat_is_rex`) is refused when the account has its own learner. There is no unlink.
- Nova messages first only on Telegram: the proactive tick selects `platform: "telegram"`.
- Account deletion removes a web-keyed learner row outright (it belongs to the account alone); a chat-keyed `MessengerUser` is still left, because Rex shares it.
- A learner with subjects and no topics is started by the learner: Home's first-session form sends the ordinary `start` with a subject they chose; on Telegram `/focus <topic>` asks which subject. Nova never guesses a subject.

## Nova on the web (Home → Start session)

The web app renders Nova's decisions; it does not make them. Three routes, all resolving the signed-in account to its Nova learner through `apps/api/lib/nova/resolve-learner.ts`:

- `GET /api/nova/today?minutes=` returns `NovaTodayView`, built by `packages/api/src/nova/product/today.ts` from the existing engines. No LLM call.
- `POST /api/nova/session` (`start` / `pause` / `resume` / `end`) and `GET /api/nova/session`: deterministic session commands. They call the same session writers a chat turn uses (`persistence/nova-persistence.ts`), so do not add a second place that writes `NovaStudySession`.
- `POST /api/nova/message` runs a normal Nova turn (used for onboarding and "tell Nova" boxes). **A sentence typed there never starts, pauses or ends a session**: `nova/entry.ts` passes `sessionCommands: "surface"` unless the text is a typed command (`/study`, `/done`), and tells the Response Brain so. The page has buttons for those; the model's reading of a sentence is not one. What the sentence says is still logged and consolidated.
- **The web path's second pass** (`brains/disambiguation-pass.ts`, one extra model call on a very unclear message) may point the reply at a topic or a kind of question. It may not turn the message into a study report, a skip, a mastery claim or a commitment: those intents are evidence and come only from the first reading. The first reading itself goes through `safeReading` on the web too.
- **"In N days" is the learner's calendar** (`calendarDaysUntil` in `engines/learner-calendar.ts`) on Today, the Planner, Telegram and proactive messages. The engines' own pressure thresholds still use elapsed time.
- **A stored date is a day, not a moment.** `addExam`/`updateExam` write the day given as noon UTC (`examInstant`); older rows are midnight UTC. `dateDayKey` reads either as its UTC day, so a learner twelve or more hours from UTC (Auckland in summer, Kiritimati) sees the day they gave; any other instant is read in their zone. `calendarDaysUntil`, the Planner's week, Progress's next exam and the web's `deadlineDate` (`components/nova/format.ts`) all use it. Held by `stored-dates.test.ts` and `nova-exams.itest.ts`.

Contracts live in `packages/api/src/nova/product/today.types.ts` (no imports, so the web app imports the types directly). UI is in `apps/web/components/nova/`; `app/(dashboard)/home/page.tsx` renders the Rex home (`components/home/rex-home.tsx`) when the status is `not_nova`. **Planner** (`GET /api/nova/planner?minutes=`, `product/planner.ts`). Home and Planner both start from `product/planning-inputs.ts`, so they show the same plan. Things to know before changing it:

- Plans are not stored. The Planning Engine (`generateStudyPlan`) is run on every request and only plans **today**; its `thisWeek` is always empty. The week view shows recorded sessions, today's blocks, reviews the retention schedule has falling due, and exams. Do not fill later days with invented blocks.
- `minutes` goes to the engine as `availableMinutes`, which refits the whole day. It can shorten a wellbeing cap but never lift one. `StudyPlan.budgetBasis` says which rule set the day's length; the "Why this plan" adjustments are worded from it.
- **The learner's time is a hard limit.** No rule raises a day above it: an exam changes what the day holds (`examCrisisMode` makes every block exam prep), never how long it is. `budgetBasis` is `preferred`, `stated_time`, `recovery`, `reentry` or `no_pressure`; there is no raised basis, and `hard-availability.test.ts` fails if one returns. Only the learner lengthens a day, by saying how long they have today (which may be more than usual) or by changing their usual time in setup.
- **When exam work does not fit, the plan says so.** `examShortfall` (Planning Engine, pure) counts the exam's topics not yet solid at `EXAM_TOPIC_MINUTES` each against today's budget plus the usual daily time for each day before the exam, inside `EXAM_WINDOW_DAYS`. `product/shortfall.ts` words it once for Today and the Planner (`PlanShortfallView`: a sentence, what it assumes, three choices) and `components/nova/shortfall-note.tsx` shows it. It is not stated on a day held short for wellbeing. The per-topic figure is an assumption and is shown as one. Telegram does not state it yet.
- Nova's context no longer carries a "recommended hours a day" figure for an exam: it ignored the learner's time.

- **Nova's model is told the same count the pages show.** The orchestrator passes `examCalendarDays` and `nextExamCalendarDays` (from `StudySnapshotResult.timezone`) to the context builder, which words a date by its kind (`## Interview: …`, `When: in 2 days`). Without them it falls back to the engines' elapsed count.
- `engines/adaptive-planning-engine.ts` is not called by anything. Its output is not applied to any plan, so the Planner does not show it.
- **The learner's changes to today** (`product/plan-overrides.ts`, owner of `NovaPlanOverride`; `POST /api/nova/planner/today`; held by `hard-availability.test.ts` and `nova-plan-overrides.itest.ts`): skip a topic today, add one (`pin`), or put the blocks in their own order. Plans are still not stored: the engine works the day out and applies these (`PlanOptions.overrides`). The day is the server's (the learner's calendar day); nothing in the request names a day or learner; a topic must be the learner's own and active; skip and add on one topic undo each other; a repeat is an upsert; an order replaces the day's order in one transaction. `planning-inputs.ts` and the orchestrator both read them, so Home, the Planner, Telegram, the proactive tick and chat plan the same day. Yesterday's rows apply to nothing. No model writes an override.

**Knowledge** (`GET /api/nova/knowledge`, `product/knowledge.ts`, UI in `apps/web/components/nova/knowledge/`). Read-only. What it shows and what it must not claim:

- **Topic identity is (subject, name).** A session's subject is the authority: a web start carries it, and `updateTopicMastery` finds the topic case-insensitively within that subject. Only a start with no subject (a chat turn) goes through `resolveTopicSubject`: the text names a subject (whole name, code, acronym, or the name as a phrase; whole words only), or the learner already has that topic under exactly one subject. Otherwise no subject and no mastery write. Never guess one.
- **How a session went** comes from the learner: the focus screen asks "How did it go?" and the answer travels as `outcome` on the `end` command to `sessionEvidence` (`study-session-engine.ts`), which maps it to the mastery engine's 0–1 input. The report records `outcome` and `evidenceBasis` (`learner_outcome` / `mastery_claim` / `unreported`). `/done` in chat has no answer and is `unreported` unless the message made a mastery claim.
- **An archived topic** (`NovaTopicMastery.archivedAt`, set by `setTopicArchived` in the topic engine via `product/topic-archive.ts`, `GET`/`POST /api/nova/topics/archive`; held by `nova-topic-archive.itest.ts`) is out of every active workflow: `getAllTopicMasteries` and `getTopicMastery` (so the plan, Today, the Planner, Telegram, the proactive tick and chat), `resolveTopicSubject`, Knowledge, the map, the extension's topic list and filing, notes' filing and `[[link]]` resolution, setup, and plan overrides. Its row, mastery, review schedule, mastery history, sessions, notes, tasks and saved pages stay. Progress passes `includeArchived` (history). Restore clears the mark; naming it again in setup (`declareTopics`) restores the same row. A new reader of topics filters `archivedAt: null` unless it shows history.
- **"Mastery" is a self-report-driven heuristic**, not a tested result, and there is no measure of how certain it is. Do not add UI copy that implies one. `reviewCount` (finished sessions that fed the topic) is the only indication of how much stands behind a number. A topic with `reviewCount` 0 has no level ("unverified").
- **One definition of "due for review"**, in `retention-engine.ts`: the schedule is the authority. A topic is due when its scheduled date has arrived (`reviewDueAt <= now`, where `TopicMasteryState.reviewDueAt` is the stored `nextReviewAt`) and overdue once it has passed. Estimated retention is not part of the rule: it only orders the due topics and appears as a reason. So "Struggled" (interval reset to one day) is due tomorrow. `isDueForReview` / `getOverdueTopics` are the only way to ask; Home, Planner, Knowledge and the proactive cron all use them, and `review-due.test.ts` fails if one grows its own comparison or retention creeps back into the rule. Callers that judge "due" at a moment other than the present pass the same `now` to `getAllTopicMasteries` and `generateStudyPlan`.
- **Self-reported sessions** (`activityType: "self_reported"`, created by consolidation from "I studied X") carry a placeholder duration. Knowledge returns `measured: false, minutes: null` for them. Home and Planner still sum that placeholder into "minutes this week".
- **Mastery history** is `NovaTopicMasterySnapshot`: one row per change `updateTopicMastery` makes (value before, value after, source, session), written in the same transaction as the change. It is that engine's record, not an input: nothing reads it back into mastery, and Progress is its only reader. `@@unique([topicId, sessionId])` means one session's report moves a topic once; a replay fails there and the mastery write rolls back with it. Topics changed before the table existed have no rows until their next write.

**Notes** (`/api/nova/notes`, `/api/nova/notes/[id]`, `product/notes.ts`, UI in `apps/web/components/nova/notes/`). A note is the learner's own content (`NovaNote`: profile, optional subject, optional topic name, title, body). The rules, each held by a test:

- **A note is not cognitive state.** Writing or editing one never touches mastery, the review schedule, `UserFact`, `UserReality`, `BehavioralPattern`, cognitive state or Learning DNA. `product/notes.ts` is the only code that reads or writes `NovaNote`, it writes no other table, and it imports no brain, orchestrator, consolidation module or LLM client (`notes.test.ts` reads the source to enforce this).
- **Note text never enters the chat pipeline.** Do not pass it to `/api/nova/message`, `handleNovaTurn`, the Understanding Brain or consolidation. Any future AI action on a note needs its own route that calls the LLM client directly and stores nothing in the note.
- **Links between notes are the text the learner wrote**: `[[Title]]` or `[[Title|shown words]]` (`product/note-links.ts`, pure, no imports, shared with the web app). Nothing about a link is stored apart from the body. `getNote` resolves each link to the learner's most recently edited note with that title, else a topic of theirs with that name, else "not written yet" (the page offers to write it), and lists backlinks: their notes whose body links to this note's title (narrowed in the database on `[[` + title, decided by the parser). A link inside a ``` block is code. Removing the brackets removes the link; deleting a note deletes no other note.
- **A save from a stale tab overwrites nothing.** The editor sends `baseUpdatedAt` (the version it opened); `updateNote` makes the update conditional on it and otherwise answers `conflict` (HTTP 409) with the note as it now stands. The page keeps both texts and lets the learner save theirs over it or take the saved one. A save with no `baseUpdatedAt` is last-write-wins, as before.
- **Unsaved text is kept in the browser** (`localStorage`, `kivo-note-draft:<id|new>`) while it is typed and offered back on the next visit; it is removed on save or discard and never leaves the browser.
- **Autosave** (`note-editor.tsx`): while a note that exists is being edited, it is saved `AUTOSAVE_MS` after typing stops, through the same guarded `PATCH` (`baseUpdatedAt`): a conflict stops autosave and shows both texts; a failure is retried after `AUTOSAVE_RETRY_MS`. Text typed while a save is on its way stays unsaved (`setSaved(sent)`), never replaced by the server's copy. A new note is created only by Save. Before Nova reads the note, the page saves what is on screen (`ensureSaved`).
- **The reader** (`components/nova/notes/note-body.tsx`) draws `#` headings, `-`/`1.` lists, `>` quotes, ``` code, `**bold**`, `` `code` ``, http(s) addresses and `[[links]]` as React elements: nothing in a note is ever treated as HTML.
- **Note templates** are `NOTE_TEMPLATES` in `product/templates.ts`, beside the study templates, ordered by `noteTemplatesFor(learningContexts)`; the notes route adds `learningContexts` to the list response for that. A template fills the editor and saves nothing.
- **Nova's help on a note** (`POST /api/nova/notes/[id]/assist`, `product/note-assist.ts`): summarise, suggest a structure, key concepts, suggest connections, or answer a question. One direct model call through the provider client, six a minute per learner, nothing stored. Sources are the note and a few related notes (`noteSources` in `notes.ts`, the only way note text leaves that file) and saved pages (`listResourceSources` in `learning-events.ts`), labelled S1, S2…; the system prompt says they are material, not instructions. Code keeps only citations of given sources and suggested links to given notes or pages; what the sources say (`fromSources`) is kept apart from Nova's own (`nova`), and `notInSources` is shown. Concepts, links and a rewritten draft are proposals: a link is added by an ordinary guarded save when the learner clicks, a draft opens in the editor unsaved. Held by `note-assist.test.ts`. The notes page no longer calls it (the tutor below replaced its panel); the route stays.
- **Nova as a tutor beside the note** (`POST /api/nova/notes/[id]/tutor`, `product/note-tutor.ts` + `.types.ts`; UI `nova-tutor.tsx`, `tutor-playground.tsx`, `tutor-session.ts`, `insert-preview.tsx`; held by `note-tutor.test.ts`, `tutor-session.test.ts` and `nova-notes-tutor.itest.ts`). Built like note-assist: one direct `gpt-4o` call per learner request (JSON mode, 20 s deadline, `TUTOR_REQUESTS_PER_MINUTE` 10 per learner, the AI allowance via `metered`), sources from `noteSources` (`bodyMax` 50 000; a long note is given as `TUTOR_NOTE_WINDOW` around the passage, `partial: true`) and, for explain/compare/connect/brainstorm/organize, related notes and saved pages; nothing stored and nothing in the chat pipeline. Modes (`TUTOR_MODES`): explain, simpler, example, steps, check, practice, evaluate, quiz, brainstorm, flashcards, summary, compare, connect, organize. Code checks the reply: a section labelled `notes` keeps that label only with a citation of a given source (else it is shown as Nova's own); each mode keeps only its own parts (`KEEP`); quiz answers must index a choice; an exercise mode needs an exercise and `evaluate` a verdict; related items are given sources. The passage is located in the saved note (`locatePassage`: marks stripped, any case, headings inside quotes count) and its heading named; the reply says which version it read (`noteVersion`, `versionDiffers`). The conversation lives in the page (`sessionStorage` `kivo-tutor:<noteId>`) and its last turns travel with each request as material. A verdict on an answer is shown only: it is not evidence and moves nothing. The panel shows only real states (saving the latest edits, one request in flight named by what was asked, waiting for an answer while an exercise is open); replies arrive whole (the client does not stream) and ease in, at once under reduced motion. **Into the note only through the preview** (`InsertPreview`): Nova's text goes in on lines of its own, as a callout naming it as Nova's, Nova's own additions marked, citations turned into `[[links]]`, where it belongs (below), never replacing anything; Undo puts the text back while nothing has been typed since. The old bottom "Ask Nova about this note" panel is gone.
- **A note's structure** (`product/note-outline.ts`, no imports, shared by server and page; held by `note-outline.test.ts`). The body (Markdown, the only copy) is read as blocks with exact ranges (`noteBlocks`: heading, paragraph, list, code, quote or callout, rule) and sections (`noteSections`). A `NoteRef` names a block of a given text by range and fingerprint; `resolveRef` finds it in the text as it is now (in place, or the same words once elsewhere) or says it is stale, and a stale one is never pointed at other text. The rendered note carries each top-level block's range (`note-blocks.ts` `at`/`to`, `data-at` in `note-body.tsx`), which is how a passage is found on the page.
- **Passages a tutor reply rests on.** The tutor reads the note as marked blocks (`markedNote`, `[b3] …`) and lists, per `notes` section, the blocks it rests on (`refs`); code keeps only blocks it was given and only on `notes` sections, and strips markers from text. The page shows them as "From your notes · <heading>"; pressing one scrolls the note to the passage and lights it (`.note-flash`, still under reduced motion) or, in the editor alone, selects it; a stale one says the passage changed. `place`: a heading of the note an addition belongs under, kept only if the note has it.
- **Where an addition goes** (`placementFor`, `resolvePlacement`, `insertAt`): a heading named or suggested, else after the passage chosen, else a summary in a summary section or a new one at the start, else the section of the passages it rests on, else (no headings) the end; otherwise a new section offered with the others to choose from. The preview says where ("Add under: Dependency Injection") with the other places; the place is found again when confirmed, and one that changed is chosen again. The end is a fallback, never the default. An addition already in the note is refused (`alreadyIn`).
- **Nova Editor** (`POST /api/nova/notes/[id]/edit`, `product/note-edit.ts` + `.types.ts`; UI `nova-editor.tsx`, switch `nova-modes.tsx`; held by `note-edit.test.ts`). Code drops changes to blocks not given, out of order or twice, outside a chosen passage (rewrite, grammar, expand, examples, dedupe, custom), and deletions when rewording; flags `large` when most of the note is rewritten (applying then needs a second look). The page shows each change where it goes (removed words struck through, new ones in Nova's colour), the learner keeps the ones they want, and applying checks each against the text on screen (`applyEdits`/`locateChange`: in place, or the same words once); if any no longer fits nothing is applied. Applied changes save through the note's guarded save, with Undo. "Work into note" on a tutor reply sends it to the Editor (`integrate`). Both modes stay mounted, so switching keeps each conversation; the mode is kept per browser (`kivo-notes-layout`).
- **Applying is saving** (`note-editor.tsx` `applyEditChanges`): the changes go into the draft the editor, preview and reader all draw (one copy), the note is saved at once through the guarded `PATCH`, and the Editor says "Applied and saved" only after that save succeeds (else "Applied on screen · not saved", with Save again). An applied proposal's diff folds away. `applyEdits` skips a change already in the text (`isApplied`: an apply sent twice, or an expansion that keeps its sentence), so nothing is made twice. Found 27 Oct: an edit typed into the Tutor (the default mode) could only be added as new text, usually at the end, and the Tutor's "organised version" was added beside the note as a second copy. Now the Tutor's reply carries `editRequest` (the model's reading, kept only for a typed question) and the page hands the request to the Editor; "Restructure my note" sends a `structure` request instead of adding a copy. Held by `note-outline.test.ts` and `nova-notes-research.itest.ts`.
- **Research papers** (`product/paper-source.ts` pure and shared; `paper-markup.ts` pure; `paper-fetch.ts`; `paper-import.ts`; `paper.types.ts`; routes `POST /api/nova/notes/papers/preview` and `POST /api/nova/notes/papers`; UI `paper-import-dialog.tsx`, `destination-picker.tsx`, `notes-commands.tsx`; held by `paper-source.test.ts`, `paper-import.test.ts`, `nova-notes-research.itest.ts`). Nothing behind a paywall or sign-in is fetched; OpenReview's browser challenge is reported, not got round. A PDF is read only on request, by the existing transcription (`transcribeForNote`, metered), or the learner uploads one; the card then says it is Nova's transcription. The modifier is the platform's own: Ctrl on a Mac is left to text fields. ⌘F stays the browser's find.
- **Reading colours** (`globals.css` `--sem-*`, `.sem-*`): one role palette in both themes for callouts and the paper (definition, takeaway, example, question, warning, source), each with its icon and label; maths is shown as LaTeX (no renderer is installed).
- **Layout**: on a screen 1024px or wider Nova is a resizable panel (`tutorWidth`, 320–720, splitter by pointer or arrow keys, kept in `kivo-notes-layout`); below, a drawer. Under 1600px with Nova docked, the notebook opens over the note instead of beside it and the editor shows Write or Preview, not Split. - **Capture and import** (`/notes/capture`, `components/nova/notes/note-capture.tsx`; `product/note-capture.ts`, pure, shared; `POST /api/nova/notes/import`, `product/note-import.ts`; held by `note-capture.test.ts` and `nova-notes-tutor.itest.ts`). One notes system: everything ends in `createNote`/`updateNote`, written by the learner's Save. A capture arrives in the address's fragment (`#url=…&title=…&text=…&via=…`, `readNoteCapture`), from the extension's Add to notes, the Send to Kivo Notes bookmarklet (`noteCaptureBookmarklet`; works in Safari on iPad), or pasted; sign-in parks it (`pending-note-capture.ts`, ten minutes, like Saved's). "Organise it with Nova" opens the note with `?tutor=organize`, which runs once. There is no iPad share-sheet target: that needs a native app.

- **Only the learner's save writes `title` or `body`.** The body is stored as typed (line endings unified, nothing else).
- **Ownership comes from the session cookie.** Every note query includes the learner's `profileId`; a note id alone never reaches a note (another learner's note is a 404). No id from the request is read as authority.
- **Study this** is the ordinary `start` command with the note's subject and topic. The session and its "How did it go?" answer are the evidence; the note is not. There is no note-to-session link in the schema.
- Search is a case-insensitive substring match. `likeLiteral` (in `topic-mastery-engine.ts`) escapes `%`, `_` and `\` wherever a name or query is compared with `mode: "insensitive"`, which Postgres runs as ILIKE.
- **Account deletion** goes through `services/accountDeletion.service.ts`, which removes the Nova academic profile linked by `telegramChatId` (cascading to notes, sessions, topics) before the `User`. It leaves the `MessengerUser` row, which is shared with Rex.

**Progress** (`GET /api/nova/progress`, `product/progress.ts`, UI in `apps/web/components/nova/progress/`). A read model answering "have I actually changed?" from records that already exist. It writes nothing, calls no LLM and takes no parameters. `/progress` is one route with two pages, like Home and Planner: a Rex account gets `components/progress/rex-progress.tsx`. The definitions, all in `progress.ts` and held by `progress-view.test.ts`:

- **Counted session**: finished, timed by Nova (`activityType` not `self_reported`) and at least `MIN_BLOCK_MINUTES` (10) long. Every number on the page uses this; the response says how many finished sessions it left out (`overview.notCounted`).
- **Active day**: a calendar day in the learner's timezone (`NovaAcademicProfile.timezone`, else UTC, via the Planner's `dayKey`) with a counted session. A chat message is never one. Weeks run Monday to Sunday.
- **Comeback**: a counted session on an active day 4 or more calendar days after the previous one (the Academic State Engine's "returning" threshold). A first session is not a comeback.
- **Consistency trend**: average active days a week over the last four finished weeks against the four before, and only when the learner had started by the first of those eight. Otherwise `not_enough_history`.
- **Topic growth**: a topic has moved when its mastery number is 10 points from the earliest recorded value that already had a session behind it. With no recorded history, direction comes from the learner's own "How did it go?" answers, and no movement is drawn. Mastery numbers and levels are the Knowledge Engine's (`masteryLevel`); Progress has no bands of its own.
- **Journey events** are derived at read time, never stored: first session, the 5th/10th/25th/… counted session, comebacks, a session that moved a topic into a higher level, and "Good" or "Crushed it" after "Struggled". Each carries the id of the session or mastery record it rests on.
- **Not shown, because nothing on record supports it**: a daily streak (the Academic State Engine owns the only one, in server time, and Home shows it), focus quality and energy (derived from pause counts; `energyTrend` is a constant), reflections (`reflectionText` is never written), goal completion (`goals` is free text with no state), behavioural patterns and reality. Learning DNA contributes only the usual session length, and only once its own `confidence` is above `low` (ten sessions).
- Sessions and mastery records are read 365 days back; older counted sessions arrive as totals from one aggregate, so the query count is fixed and the response does not grow with history.

**Learning DNA** (`GET /api/nova/learning-dna`, UI in `apps/web/components/nova/learning-dna/`). How this learner studies, as beliefs that carry their own support and can change. One owner, three files:

- `engines/learning-dna-engine.ts` (pure) computes every signal. Nothing else may: Progress shows the stored session length, it does not work one out (`learning-dna.test.ts` reads the source to hold this).
- `persistence/learning-dna-store.ts` is the only reader of DNA evidence and the only writer of `NovaLearningDNA`. `refreshLearningDna` runs when a session ends (`consumeExecutionReport`); reading writes nothing.
- `product/learning-dna.ts` lays the signals out for the page and holds the timezone write.

The rules that keep one unusual day from becoming a belief, each with a test:

- **Evidence** is counted sessions (`isCountedSession` in `study-session-engine.ts`, shared with Progress) from the last 90 days, at most 60. Older sessions leave the window, so a belief nobody renews fades.
- **Levels**: `unknown` below 5 pieces of evidence, `emerging` from 5, `supported` from 10, `strong` from 20. A signal at `unknown` has no value; it says what it would need.
- **Typical values** are a median with its middle half, never an average.
- **Comparisons** ("this length goes better") use only the learner's "How did it go?" answers, need 4 answered sessions on each of two sides and a 20-point lead, and are as confident as their smaller side (4 / 8 / 15). Otherwise there is no conclusion.
- **Weakening**: every conclusion is rechecked against the latest sessions (the last 8, or the latest half for comparisons). Disagreement marks it `weakening` before it changes.
- **Time of day** is claimed only when `NovaAcademicProfile.timezone` holds a real zone. The setup conversation never asks, so the learner's device reports it once through `PUT /api/nova/timezone`; it is stored only while none is stored and cannot be moved by a later request.
- `NovaLearningDNA.signals` is bookkeeping (since when a conclusion has held, what it replaced), not the conclusions: those are recomputed from sessions on every read. The older columns (`optimalSessionMinutes`, `planAdherenceProfile`, `dataPointCount`, `confidence`) are filled by `legacyDnaColumns` from the same signals.
- **Not computed, because nothing on record supports it**: distraction, burnout, preferred formats, focus, energy. The page lists them under "What Nova doesn't know". Do not derive them from pauses, short sessions or gaps.
- `preferredStudyTime` is what the learner said in setup. It is shown as their statement and feeds no signal.
- Learning DNA is not memory: it writes no `UserFact`, `UserReality`, `BehavioralPattern` or mastery, and a future source of evidence (a browser extension's learning events) should arrive as sessions or as a new evidence type in the store, not as a second calculation.

`engines/learner-calendar.ts` holds the day, week and clock-hour helpers Planner, Progress and Learning DNA share.

**Browser extension and learning events** (`apps/extension`, `product/learning-events.ts`, `product/extension-connection.ts`, web UI in `apps/web/components/nova/saved/`). The extension is a context bridge: it sends what the learner explicitly asked for and decides nothing.

- **A learning event is a record of an action, not evidence of learning.** `resource_saved` and `study_requested` are the only types. `learning-events.ts` is the only code that touches `NovaLearningEvent` and writes no other table: no mastery, session, Learning DNA, fact, reality, pattern or note, and no engine reads events (`learning-events.test.ts` reads the source to hold this). Do not add a `page_viewed` type or derive anything from event counts.
- **Study this starts nothing by itself.** The extension posts `study_requested` and opens `/focus?study=<eventId>`; the Focus screen shows the page and its subject and topic, and the learner's click sends the ordinary `start` command. There is still one place that opens a session.
- **Filed under nothing by the learner** (`PATCH /api/nova/learning-events/[id] { unfile: true }`, the map's Unlink): subject, topic and `filedBy` cleared; the page itself stays saved.
- **Only this is stored about a page**: its address (http/https only, with login, fragment and credential parameters removed by `normalizeResourceUrl`), its title, the site (derived from the address), and the subject and topic the learner chose. The request body is capped at 8 KB and every field not in `LearningEventInput` is ignored. The server never fetches a saved address.
- **Idempotency**: `clientEventId` is unique per learner. A retry returns the stored event and writes nothing; it cannot rewrite it. Saving an address that is already saved re-files that one entry.
- **Rate limit**: 20 events a minute per learner, counted in the table.
- **The extension has its own credential, not the web session.** The signed-in web app makes a one-time pairing code (`POST /api/nova/extension/pair`), the learner types it into the extension, and `POST /api/nova/extension/connect` exchanges it for a bearer token. `NovaExtensionConnection` stores SHA-256 hashes only. The token opens `GET /api/nova/extension/context`, `POST /api/nova/extension/disconnect` and `POST /api/nova/learning-events`, and nothing else; it dies on disconnect or after 30 idle days. `apps/api/lib/nova/extension-access.ts` resolves it to a learner through the same `companionOf` rule as the cookie. Do not accept it on any other route.
- **Those three routes and `connect` answer cross-origin requests from an extension's own origin only**, `chrome-extension://` (Chrome, Edge, Brave, Arc) and `safari-web-extension://` (Safari), because the extension asks for no host permission. They never take the session cookie. Do not add these headers to a cookie-authenticated route.
- **That origin rule is one constant**, `EXTENSION_ORIGINS` in `apps/api/lib/nova/extension-access.ts`: a list of schemes, held by `extension-origin.test.ts`. Another browser's extension origin is refused until its scheme is added there. Never a wildcard, and never a web origin.
- **Safari runs the same `dist/`**, wrapped in a Mac app by the Xcode project in `apps/extension/safari/` (`npm run build:safari --workspace nova-extension`). The project refers to `dist/` and holds no copy of the source; do not fork the extension for Safari or add native code to the wrapper. Safari exposes the same `chrome.*` calls. It is signed to run locally only (Safari needs "Allow unsigned extensions"), is macOS only, and has not been submitted anywhere: see the extension's `README.md`.
- **Add to notes** in the popup opens `/notes/capture` with the page and selection in the fragment (`openNova`); it makes no request and uses no credential, so the web page saves it with the ordinary session.
- **Extension permissions are `activeTab` and `storage`.** No host permissions, content scripts or background script; `apps/extension/test/extension.test.mjs` fails if one is added or if the code reaches for another browser API. Its Nova address is fixed at build time (`NOVA_URL`).
- Site-specific behaviour (a video's progress, a solved problem) belongs in a new adapter in `apps/extension/src/lib/page.js` plus a new event type handled in `learning-events.ts`, not in special cases.

Session rules that must hold:

- **One meaning of "session ended".** The web End button is `/done` without a chat turn: `persistSessionEnd` builds the same command-established `study_report` signal, routes it through `computeSessionAction` and the shared `sessionLifecycle` (the function `persistTurn` uses), and hands the same evidence to `consolidateTurn`. Do not write a second end path.
- **One clock.** `engines/session-clock.ts` defines study time (`sessionElapsedSeconds`). Paused time is kept in `NovaStudySession.totalPausedSeconds`; `totalPausedMinutes` is only its floor. Pause and resume are written only by `pauseStudySession` / `resumeStudySession`.
- **One open session per learner.** `openStudySession` checks and inserts inside a transaction that first takes `SELECT … FOR UPDATE` on the learner's `NovaAcademicProfile` row. Every start (web or `/study`) goes through it. Do not create a `NovaStudySession` anywhere else.
- **Conditional writes.** Pause, resume and end use `updateMany` guarded on the expected state, so a repeated or concurrent command writes nothing and an execution report is consumed once.

## Nova on Telegram

Full description: `docs/NOVA_TELEGRAM_MENTOR.md`. Telegram is a surface: it owns no session, plan, mastery, memory or timer, and every state change goes through a function the web app also calls. The rules, each held by `telegram-mentor.test.ts` or `nova-telegram.itest.ts`:

- **Three inputs, one path each.** A command and a button tap are protocol and call no model. Anything else is text: one Understanding Brain call with a context block (date, running session, open question), then `decision/action-decision.ts` (pure), then the same actions the buttons run, then the canonical turn (`runNovaOrchestrator` with the reading passed in as `understanding`). Do not add a regex, keyword list, yes/no check or second classifier anywhere on this path.
- **A reading is a proposal, and the model's confidence is not permission.** The request envelope (`LearnerRequest` in `types/understanding.types.ts`) is a closed vocabulary validated by `parseLearnerRequest`, and it says how readable the message was (`clarity`) and whether it takes itself back (`changeOfMind`). `decision/interpretation-safety.ts` (pure) decides what of a reading may be used: an `unintelligible` one is replaced by a neutral reading and never reaches the canonical turn. `decision/action-decision.ts` then checks each action's preconditions against the reading and the real state: a start needs an explicit request naming a topic on today's plan (or the answer to a Start option), time alone never starts anything, minutes against an open offer re-offer it, and ending a session or adding an exam never runs from a sentence. To change behaviour, change a precondition there; do not add a rule for a phrase.
- **An open offer to start is not sent again by conversation.** While a `start` or `nudge` prompt is open, a reading of "what now" from a message the reading does not call a `plan_request` is answered in words (`converse`, reason `offer_already_open`) and the open offer stays as it is; stress read as "something else" with no topic is answered as a feeling (`feeling_not_alternative`). An outright plan request, a new length, a start request, `/today` and the buttons still act. Found on 14 October: "acha chl bta requirements" read as `what_now` re-sent the Start menu. Held by `telegram-mentor.test.ts` and `nova-telegram.itest.ts`.
- **A request of its own is not an answer to the open card** (rule 0 of `decideAction`). Envelope v6 adds three requests: `week_plan` (the next seven days), `change_plan` (change today's plan or goals) and `progress` (how they are doing over time). These, and `something_else` naming a topic, act whatever `promptAnswer` the reading attached; the week and progress leave the card open. Words that cannot be placed while a card is open still get "use the buttons above" and leave the card as it is: the eval shows those are short replies to the card ("do it"), and the reported phrases are read clearly as requests of their own. Found on 17 October: the week came back as today's card, "update today's goals" was ignored, "kuch Deep Learning se related bata" got the plan's next block. Held by `nova-telegram.itest.ts` ("Reported failures") and `telegram-mentor.test.ts`.
- **The week** (`/week`, `showWeek`) is the Planner's read model built from today (`loadNovaPlanner(…, { ahead: true })`, `daysFrom`) plus `listTasks`: today's planned blocks, finished sessions, tasks by due day, reviews falling due and dates, each labelled as what it is. Only today is planned; nothing is invented for later days.
- **The command menu is per chat** (`setMyCommands` with a chat scope, `NOVA_CHAT_COMMANDS`): set when the chat is linked, and set again when the learner sends `/start` or `/help`, so a chat linked before `/week` and `/progress` existed gets them. Never the bot-wide default: Rex chats share the bot. A chat that sends neither keeps its older menu; typing the command still works.
- **Progress** (`/progress`, `showProgress`) is `loadNovaProgress` (counted sessions this week, the last finished weeks, since the first session, the consistency trend, `changes`, what was not counted) with today's done and planned minutes from the Planner, said apart. No streak, no mastery claims beyond Progress's own lines.
- **Changing today from chat** (`changePlan` → `applyPlanChange`) writes only through `changeTodayPlan` (`product/plan-overrides.ts`). Asked with nothing named, it lists the plan with Skip / First / Change my time; a named topic on the plan is offered to leave out, one of theirs off the plan to add, one not theirs to add to a subject (the setup offer). A time is the recorded stated time (`showToday`). The tap applies it, the plan is read back, and the reply says what the plan now shows (with Undo for skip and add). Option `plan_change` carries the topic id; `changeTodayPlan` checks it is the learner's own and active.
- **A different topic named** (`alternativeFor`) is matched to the learner's own structure by `topicsNamedBy` (topic-mastery engine, whole words: a subject named or holding the name, or a topic that is, holds or is held in it). A planned block among them is offered first, then their topics with Start buttons; a name on record nowhere is said to be so and offered as an addition (setup offer). Never the plan's next block.
- **Ending needs an outcome.** `/done`, End and "I finished" ask "How did it go?"; the answer calls the ordinary `end` command with that outcome. There is no unreported end from Telegram.
- **One open prompt per learner** (`NovaTelegramPrompt`, `telegram/prompt-store.ts`). A button carries `p:<promptId>:<optionId>` and nothing else; what it does is read from the row. Resolving is one conditional write.
- **No process memory.** The turn lease, action limiter, model budget and delivery state are `NovaTelegramChannel` (`telegram/channel-store.ts`).
- **`sessionCommands: "surface"`** tells the turn that the surface runs session commands, so `sessionLifecycle` starts and ends nothing. Use it for any surface that calls `runNovaSessionCommand` itself.
- **`scriptedReply` / `directive` / `responseFallback`** on the orchestrator input: a product result is stated without the Response Brain; a decided action is handed to it to word; a model failure falls back to the plain statement. The Response Brain never chooses the action.
- **Register** (`decision/register.ts`) is chosen by code and applies to every Nova reply, web included. Playful needs the learner's explicit "push me hard" and nothing serious going on.
- **`topic_struggle`** is a signal with no wording pattern: only the Understanding Brain's `struggleTopic` establishes it. Consolidation turns it into a soft mastery observation, at most once per topic per 20 hours, never a `UserFact`.
- **Stated time** ("I've only got 30 minutes") is `NovaAcademicProfile.statedMinutes` for that local day, read and written only by `product/planning-inputs.ts`; a `minutes` parameter still wins.
- **An exam date is moved, renamed or removed** on `/settings/study#exams` (`components/nova/exams-editor.tsx` → `GET /api/nova/exams`, `PATCH`/`DELETE /api/nova/exams/[id]` → `listExams`, `updateExam`, `removeExam` in `product/exams.ts`, the only code that changes a `NovaExam`). The id selects among the learner's own exams (`where: { id, profileId }`, guarded `updateMany`/`deleteMany`), `checkExamChange` (pure) decides what a change may be, and each write answers with the list as it now stands. Removal deletes the row: nothing hangs off an exam, and there is no archive column. Nothing about a plan or reminder is stored, so nothing is undone: every page and the proactive tick read exams afresh, and an unworded countdown claim whose exam is gone is dropped. Held by `exam-editing.test.ts` and `nova-exams.itest.ts`. Telegram cannot move or remove an exam.
- **Exams after onboarding** are added by `product/exams.ts`, only on the learner's confirmation, always under one of their subjects. `examToOffer`: a label naming one subject is offered under it; a label naming none is offered with their subjects to choose from, unless an exam is already on that day (then that one is meant and nothing is offered). So "exam is tomorrow" can never create a second or subject-less exam.
- **The Response Brain is told what happened.** It words a result only when the operation succeeded; a turn with no action carries a directive saying nothing was done.
- **Proactive and what is going on in the learner's life**: only circumstances that will pass (expiring within 15 days) gate messages; a standing one (a job) shapes the plan and does not silence Nova. Illness, injury or an emotional constraint: nothing is sent, an exam countdown included. A life constraint (a family matter): study nudges are held, and an exam countdown goes out as the date only (`informOnly`: no recommendation, no Start button). Instructions for the model go in the prompt, never among `facts`, which the no-model fallback sends as they are.
- **Proactive**: a message approved earlier and not yet delivered is re-checked with `holdReason` before every retry. `decision/proactive-decision.ts` (pure) generates every candidate, gates, then ranks. `proactive/proactive-outbox.ts` is the only writer of `NovaProactiveMessage`: claim by unique occurrence key, word, store, send. Only delivered rows count toward the cap of two a day. No timezone means no proactive message. Do not add a type without a fact on record behind it, and do not compare clock minutes for equality.
- **In production Nova ignores updates without a valid `TELEGRAM_WEBHOOK_SECRET`.** `NOVA_PROACTIVE_DISABLED=true` stops Nova messaging first.
- `scripts/novaTelegramEval.ts [repeats] [group] [raw]` runs real phrases through the configured model, the parser, `safeReading` and `decideAction`, and prints the decision and what it would write. Each case names the decisions that would corrupt state; the run exits 1 on any. It is the only check of what the model actually reads: run it after changing the Understanding prompt or the action decision.

## Talking to Nova: one reading, one decision, both surfaces

A sentence typed to Nova takes the same path on Telegram (`telegram/telegram-turn.ts`) and on the web (`interaction/web-sentence.ts`): one Understanding call with context, `safeReading`, `interpret`, `decideAction`, the shared action functions, then the canonical turn. The rules, each held by `semantic-interaction.test.ts` or `nova-semantic.itest.ts`:

- **The kind of a message is derived, not classified twice.** `interaction/semantics.ts` (pure) names a reading (`general_question`, `learner_question`, `action_request`, `context_signal`, `reality_signal`, `emotional_signal`, `onboarding_input`, `status_request`, `conversation`, `unsupported`, `unclear`) from fields the Understanding Brain already filled. The model adds three fields to the request envelope (v4): `asks` (`knowledge` / `about_me` / `none`), `availableMinutesMax` (a range) and `setup`. (v5 adds `language`; see "Reply language".) A kind describes; it authorises nothing.
- **Focused context.** `contextNeeds` says which parts of the learner's record a reply may use, and `buildFocusedLayer` in the context builder includes only those. A general question gets the last few lines of the conversation and nothing else. The orchestrator takes this as `focus: { needs, facts, mode }`; without it, it builds the whole layer as before.
- **A general question** ("what is deadlock?") decides `explain`: no product action, `mode: "explain"`, and the Response Brain answers the question. It reads and writes nothing of the learner's.
- **A learner question about a topic** ("should I study deadlocks tonight?") decides `advise`. `interaction/advice.ts` (pure) finds the topic in the Today view and returns the verdict, its sentence and the facts behind it; the Response Brain may reword the sentence, with those facts as the only figures it may state.
- **A range of time** ("20-30 mins") decides `ask_minutes`: both ends are offered and neither is recorded until one is picked. A single stated time is offered as its own Start length next to the standard ones.
- **Study setup is offered, never saved from a sentence.** `product/setup.ts` is its one reader and writer: `proposeSetup` (pure) turns a `setup` statement into a proposal under a subject of the learner's own, the `confirm_setup` prompt shows it back, and `applySetup` runs on confirmation, in one transaction, idempotently. Topics are created by `declareTopics` in the topic mastery engine with no mastery, no review and no snapshot.
- **What is still missing** is `interaction/initialization.ts` (pure): of subjects, topics, exams and usual study time, what is not on record and which one thing to ask for next. An empty plan asks that question. Nothing on record is asked for again.
- **The Planning Engine schedules syllabus topics that were never studied** (`new_material`): two when the plan is otherwise empty, one otherwise, in the order they were given.
- **The web page's contract.** A sentence typed on the web runs no session action (`PAGE_BUTTONS_ONLY`): it is answered in words and pointed at the page's buttons. The web answers in words only questions it asked there (`WEB_PROMPTS`: saving setup, adding an exam, picking a length), so a typed "yes" cannot accept a Start offer made on Telegram.
- **Two model calls per turn at most**: the reading, and the wording. The web path no longer runs the second-pass disambiguation; only a typed slash command still takes the older turn.
- The action functions both surfaces call live in `telegram/telegram-actions.ts` and the prompt store in `telegram/prompt-store.ts`. They are channel-neutral in behaviour; the directory name is historical.

## The first message in a linked Telegram chat

Held by `first-use.test.ts` and `nova-first-use.itest.ts`.

## Reply language (English and Hinglish)

Held by `reply-language.test.ts` and `nova-language.itest.ts`. Nova answers in the language the learner writes in. Language is wording: the decision, every name and every figure are the same in both.

- **Who says which language a message is in:** the Understanding Brain, as `request.language` (`english` / `hinglish` / null when a message is too short to tell, such as a number, "ok" or a bare topic name). Envelope v5. There is no keyword list and no script check on the learner's words.
- **When the reading names no language** (`chooseLanguage` in `interaction/language.ts`): a message too short to tell (fewer than `SENTENCE_WORDS`, 4, words with letters: "ok", "30", a topic name) keeps the conversation's language; a longer one is answered in English, the default, never in the previous message's language. The same rule picks the language of the "can't read messages" line before a reading, and the language the reply used is what the log stores, so the next short message follows it. Found on staging (18 October): "How is my progress going?" and "remind me at 8 pm to study" came back with no language after a Hinglish message and were answered in Hinglish. Held by `reply-language.test.ts` and `nova-telegram-acceptance.itest.ts` S65–S72.
- **Where it is kept:** the conversation's language is not stored anywhere new. The canonical turn stores it with the user message in the conversation log (`metadata.language`), and `loadReplyLanguage` in the conversation adapter reads the latest one. Writing in the other language switches at once.
- **The language they chose** (onboarding / Settings, `onboardingAnswers.language`, read by `loadVoicePreferences`) is the default, never an override: what they write in still wins. It replaces English where nothing else decides (`chooseLanguage(…, preferred)`: a sentence the reading could not place), starts a conversation with no language in the log (`loadReplyLanguage(userId, fallback)`), and is the language of a proactive message. On the web the Response Brain's directive now carries the same `languageLine`; lines code wrote stay English there.
- **A reply the Response Brain words** (a conversation turn, the first message, a proactive message) gets one extra line, `languageLine` from `interaction/language.ts`. English adds nothing.
- **A reply code wrote, to a typed message** (the plan, an advice sentence, a setup question) is said in Hinglish by `brains/language-wording.ts`: one `gpt-4o-mini` call given only that text. `faithful` throws the rendering away unless it carries exactly the same figures, is in Roman letters and has not grown; then the English text goes out. It spends from the daily wording budget and never runs on a turn the Response Brain worded, so a turn is still two model calls at most.
- **Commands and buttons call no model**, in either language. Their fixed lines (`TEXT_HINGLISH` in `telegram-replies.ts`, one for every line of `TEXT`) are in the learner's language; the plan, status and session lines go out as code wrote them.
- **Button labels, topic names, numbers and dates are never translated.** The web chat's fixed lines stay English.

## Telegram hardening: what real use showed

Held by `telegram-hardening.test.ts` and `nova-hardening.itest.ts`.

- **A sentence never sets a reminder.** Rex's `CustomReminder` is not used: it parses times with regexes and a second model call, falls back to `Asia/Kolkata`, and is sent with no outbox or retry. So a request for one in chat is read (`request.action = "set_reminder"`), decided (`reminder_unavailable`, before every other rule, so it is never a "not today") and answered by code with `TEXT.reminderUnavailable`: nothing was scheduled. It is never worded by the model. Reminders exist only on calendar events the learner makes on the web (see "Calendar and reminders"), delivered through the outbox under their own type.
- **The Response Brain may not claim or promise an action** (static layer rules 11 and 12): nothing was done unless the prompt says so, and nothing is said about the student that is not on record.
- **A length of time in a worded reply must be one Nova gave it.** `groundDurations` (`brains/grounded-reply.ts`, pure, character checks only) runs on every Response Brain reply in the orchestrator, after the model and before the reply is sent: a sentence stating a number of minutes or hours that is not a length in the context, the prompt or the learner's message is taken out (logged as `ungrounded_duration_removed`); a reply with nothing left becomes `UNGROUNDED_REPLY_FALLBACK`. A number that is not a length (a score, a topic count) grounds nothing. Lengths repeated from Nova's own earlier reply in the conversation history count as given.
- **A topic a worded reply recommends must be one Nova gave it.** The Response Brain returns `recommends` (every topic, chapter, concept or resource its reply tells the learner to study or do next). `groundTopics` (same file, pure) takes out each sentence naming a declared name that is not in the context, the prompt or the learner's message (logged as `ungrounded_topic_removed`); matching is whole words, any case, a plural "s" ignored. When the context carries `NOTHING_RECOMMENDED`, only the learner's own message grounds a name, and every one of their topic names is checked too, so a topic the model names without declaring it is still caught. Outside that case an undeclared name is held back by rule 13 alone.
- **When nothing recommends what to study,** the context says so (`NOTHING_RECOMMENDED` in the context builder): suggest no topic or length, point to Today. Not added for a question about the subject matter, or when a surface's facts or the plan are in the context. A conversation whose reading is `plan_request` now gets the plan (`contextNeeds`). Held by `grounded-reply.test.ts`.
- **One update, one reply.** `deliver` in `telegram-turn.ts` drops and logs a second reply to the same update, and the last-resort "that didn't go through" line is sent only when nothing has been.
- **Noise and a model that is down are different replies.** Noise (`clarity: unintelligible`) is "I didn't catch that", with the fixed choices once and no second set while those are open. A reading that failed is `TEXT.notUnderstood`, which says the commands still work. In production, repeated `understanding_failed` in the log means the model provider is refusing calls (a quota or rate limit), not that the messages were unreadable.
- **A model call has a deadline** (`deadlineMs` on the one LLM client; 6 s for a reading, 8 s for wording, `NOVA_UNDERSTANDING_DEADLINE_MS` / `NOVA_RESPONSE_DEADLINE_MS`). Every attempt and every wait between attempts fits inside it, so a rate-limited provider fails in time for the turn to answer. Callers that pass none (Rex) are unchanged.
- **A session stopped before ten minutes** is ended and rated like any other and is kept, with the learner's answer, on the session. It moves no mastery, reschedules no review and writes no mastery history (`countedAsStudy` on the execution report, decided in `study-session-engine.ts` with the same `COUNTED_SESSION_MINUTES` Progress and Learning DNA use). Both surfaces say so (`ended.counted`).
- **The reply is sent before the turn is recorded.** A reply code wrote goes out before `runNovaOrchestrator`; a worded one goes out from the orchestrator's `hooks.reply`, before `persistTurn`. Recording still runs and is still awaited inside the same request: nothing is left running after the webhook returns.
- **Typing** is the webhook's existing indicator. It stops when the reply is sent (`onReplied`), not when the turn has been recorded.
- **Where the time went** is on the one `nova_telegram` log line: `timings` (`webhookMs`, `learnerMs`, `contextMs`, `understandingMs`, `decisionMs`, `actionMs`, `responseMs`, `telegramSendMs`, `replyMs`, `persistMs`, `totalMs`), `modelCalls` and `slowStage`. `replyMs` is what the learner waits. `scripts/novaTelegramLatency.ts` turns a log download into P50/P95 per kind of update.
- **A second message sent while the first is still being recorded** gets "Still on your last message". The turn lease is unchanged; waiting for it needs a timer, which `telegram-mentor.test.ts` forbids in these files.

## Tasks and the Planner's board

Held by `tasks.test.ts` and `nova-workspace.itest.ts`. The Planner has two tabs: the study plan the engine works out, and the learner's own task board (`/planner?view=board`).

- **`NovaTask` is the learner's to-do list** (title, status `todo` / `in_progress` / `done`, priority, subject, topic name, due day). `product/tasks.ts` is its only reader and writer; routes are `/api/nova/tasks` and `/api/nova/tasks/[id]`.
- **A task is only a task.** Making, moving or finishing one writes that row and nothing else: no session, no mastery, no exam, no stated time. The Planning Engine does not read tasks, so moving a card never changes the plan. Do not feed tasks into planning or evidence without a decision to; a finished task about a topic is not a session on it.
- **A due day is a calendar day** (`dueDay`, `YYYY-MM-DD`), counted from the learner's own today (`dueInDays`).
- **`clientKey` makes a create idempotent** (`@@unique([profileId, clientKey])`): a double click, a retry or a template applied twice returns the task that exists, as it now is.
- **A wait from the learner** (`PATCH /api/nova/tasks/:id { waitFor }` adds, `{ stopWaitingFor }` removes just that wait; the map's Connect and Unlink): one wait added through `addWaitsIn` (the one writer of `NovaTaskDependency`), in a transaction with the rest of the update; on itself, round a circle or on a task not theirs is `bad_wait` and writes nothing; a wait already there changes nothing. The reply's `after` shows it, and the web checks that before saying it was saved.
- **A task's expected time** (`estimatedMinutes`, 5–600) is only what the learner gives; nothing guesses it. **Their own order** (`position`) is set per open column by `reorderTasks` (`POST /api/nova/tasks/order`): one transaction, each write guarded on the task still being theirs and in that column, refused whole (409) otherwise. `compareTasks` puts placed tasks first. Today says when the tasks due today (with a stated time) and the study plan exceed the day's time, and moves nothing. Held by `tasks.test.ts` and `nova-task-order.itest.ts`.
- The board (`components/nova/tasks/`) moves a card by drag and drop or by the arrows on it; both are the same `PATCH { status }`. Home's "Your tasks" is the same rows.
- **From Today** a task can be edited (the board's `TaskEditor`), moved to tomorrow with Undo (`nextDay` in `task-format.ts`, an ordinary `PATCH { dueDay }`), or ticked done. **Choose another** (`components/nova/choose-another.tsx`) starts any of today's other blocks or any topic of the learner's with the ordinary `start`; the plan itself is unchanged.

## Getting back on track (recovery)

Held by `recovery.test.ts`, `hard-availability.test.ts` and `nova-recovery.itest.ts`. `engines/recovery-engine.ts` (pure), `decision/plan-change-policy.ts` (pure), `product/recovery.ts`, `GET`/`POST /api/nova/recovery`, UI in `components/nova/recovery-card.tsx` (Today).

- **Where the learner is** comes from calendar days with a counted session (`countedStudyDays`: finished, timed, ten minutes or more, in the learner's zone): `on_track` (today or yesterday), `missed_one`, `missed_several`, `returning` (four or more days, Progress's comeback threshold), `no_history`. A self-report, a short session, a saved page or a finished task is not a study day.
- **One policy for what may change** (`classifyChange`). *Automatic*: only today's computed plan, never stored, only shorter, not over a time the learner stated today, not while an exam or certification takes the day. *Needs approval*: a change to a record the learner set (a task's due day). *Refused*: lengthening a day, moving or removing a deadline, moving a task into the past, onto an exam day, past its subject's next date, or a finished one.
- **A first day back is a re-entry day** (automatic): `PlanOptions.reentry` makes the usual day half as long (`reentryMinutes`, never under `MIN_BLOCK_MINUTES`, never longer), basis `reentry`. Set in `planning-inputs.ts` and the orchestrator from the same `studyGap`, so Home, the Planner and chat agree. It does not stack on `recovery` or `no_pressure`, and ends with the next counted session. Nothing is written.
- **Overdue tasks are a proposal** (needs approval). `proposeTaskMoves` places open overdue tasks from today on: high priority first, at most as many due a day as the learner has ever finished in one day (`mostTasksDoneInADay`, at least 1, said as an assumption), exam/certification days left free, a task filed under a subject before that subject's next date. A task with no such day is reported (`deadline_conflict`, `no_room`), never squeezed in.
- **The proposal is not stored.** It is recomputed from the record on every read and identified by a fingerprint of exactly its moves (`proposalId`), so a reload, a second tab or a repeated trigger gives the same proposal and creates nothing, and the active plan and tasks are untouched while it waits.
- **Accept** (`{ action: "accept", proposalId, moves }`) applies only if the record still gives that id; the server applies its own moves, each re-checked by the policy, through `moveTaskDueDays` in `tasks.ts` (one transaction, each move guarded on the task's current due day and being open). A retry or a second tab gets `already_applied`; a changed record gets 409 `changed` with the proposal as it now stands and nothing written. **Undo** sends back the accepted moves and is the same guarded write reversed (`undone` / `already_undone` / 409). **Not now** writes nothing: it hides that proposal id in this browser only.
- **Nova's model** is told the calendar gap and, on a re-entry day, `REENTRY_LINE`: code shortened the day, any task moves wait for the learner, and it cannot accept them.
- Decisions are logged (`{"layer":"nova_recovery", event}`), not stored: a durable decision record, a remembered "no" across devices and a proactive "welcome back" need a table (schema request in `audit/phase2-tracker.md`).

## Focus context and the session note

Held by `focus-context.test.ts`. `product/focus-context.ts`, `GET /api/nova/focus-context`, `POST /api/nova/session/reflection`, UI in `components/nova/focus-context.tsx` and `session-note.tsx`.

- **Focus context is a read model of what the learner filed under a topic**: their open tasks, their saved pages, their notes (titles only, through `listNoteLinks`), the subject's next exam, and their note from the last session on it. It is shown under Today's recommendation and on the Focus screen. Something belongs when it is filed under the same subject and either that topic or no topic; with no subject nothing is shown. It reads tasks, saved pages and exams only through `listTasks`, `listResourceLinks` and `listExams`, writes nothing and calls no model.
- **Showing a record is not evidence.** A task finished or a page opened moves no mastery. The page says so.
- **A task can start a session** when it names both a subject and a topic (the Focus button on Today's task list). It sends the ordinary `start`; ticking the task is still only a task.
- **The session note** is three optional short answers after ending a session (what got done, what got in the way, the next step), stored as JSON text in `NovaStudySession.reflectionText` by `saveSessionNote` in `persistence/nova-persistence.ts`. Written once, by a guarded write on the learner's own finished session without a note, so a retry or a double submit changes nothing. `ended.sessionId` on the session response is what the page attaches it to.

- **Not connected yet:** a task has no link to a goal or to a specific exam (both would need a column), and Telegram shows none of this.

## Knowledge Map

Held by `knowledge-map.test.ts` and `nova-workspace.itest.ts`. `/map`, `GET /api/nova/knowledge-map`, `product/knowledge-map.ts`.

- **A read model of links that are stored.** Nodes are subjects, topics, notes and saved pages. Edges are: a topic's subject; a note or saved page filed under a subject; and under a topic when it names one of that subject's topics (compared trimmed, single-spaced, any case). Nothing is inferred and no edge is added for looks. What is filed under nothing is drawn unconnected, and the view says how many such items there are.
- It writes nothing, calls no model, and reads notes and saved pages only through `listNoteLinks` and `listResourceLinks` in their owning modules. A note's body never reaches the map: `listNoteLinks` reads it inside `notes.ts` only to return the titles it links to (`linksTo`).
- **`links_to` edges** are those `[[links]]`: note → the note of that title (most recently edited when two share one) or → a topic of that name. They are drawn as a quiet line with a **ring where the link arrives** (the backlink marker; the edge stays an edge, nothing is added to the data) and do not place anything in the layout. A filter hides them, and the detail panel names each relationship ("Links to this", "Its topic"…).
- **Scoped view:** "Show what is around it" (a card with nothing inside, or `?focus=<node id>`) shows an item, what it sits inside and what links to it. Search matches a node's name, subject, topic and site.
- **Exploring inside a card** (`explore.ts`, pure; held by `explore.test.ts`): a card with something inside it opens as a map of itself and its descendants (Explore, Shift+Enter, double-click). It is a view of the same map, never a copy: cards keep their places from the whole map, so going in is a zoom, and an edit inside is the one map's edit. A stack of views keeps the pan and zoom each was left at (Back restores it; Up goes to the card it sits inside; breadcrumbs name the path). `?explore=<node id>` reopens it. A link from inside to a card outside is kept as it is and drawn to a round marker beside the map; the marker goes to that card. A view of a card that is gone or emptied closes.
- **Adding and deleting from the map** (`map-structure.ts` plans, pure, held by `map-structure.test.ts`; `map-structure-api.ts` sends; proven on Postgres by `nova-map-editing.itest.ts`, which plays the web's own planner). Only through the routes that own the records: Subject Studio's versioned batch (`POST /api/nova/subjects`: `add_subject` with a parent, `add_topics` inside or beside, `update_topic` for a description, `move_topic` + `remove_topic`, `remove_subject`), the task routes (a step under a task, a task filed under a topic; `clientKey` per dialog so a double submit makes one) and the archive route. No new route and no schema change. Deleting: a task's steps are kept as tasks of their own by default, or go with it once ticked; a topic with topics inside is deleted alone by default (they move up in its place) or as a branch once ticked, deepest first; anything with recorded study (archived topics included) is never deleted: a studied leaf is offered Archive instead; a subject goes only once empty. A changed structure (409 `stale`) deletes nothing and reloads the map.
- A topic has a level only when a session stands behind it; one with none is drawn as a dashed ring.
- **A node opens its own record**, never a list to search again: a note at `/notes/<id>`, a topic at `/knowledge?topic=<id>` (the row opens and scrolls into view), a subject at `/knowledge?subject=<id>`, a saved page at `/saved?page=<id>` (its row is marked). The pages read those ids from the address in an effect.
- **From a topic node** the learner can start a 25-minute session (the ordinary `start`, through `useStartSession`) or write a note filed there; from a subject node, a note. Nothing can be linked, unlinked or scoped to a goal from the map: goals are free text with no id, and re-filing is done on the note or saved page itself.
- **Keyboard** (`map-shortcuts.ts`, one list read by the handler and the `?` panel; held by `map-shortcuts.test.ts`). `/` or ⌘K/Ctrl+K find (the map page mounts no command palette); arrows move between connected cards along the drawn tree (pan with nothing selected; Shift+arrows always pan); Enter explores the card chosen last (a card with nothing inside opens its details instead; repeats of a held key are ignored); Shift+Enter opens details; U goes up; Space folds; `+`/`-` zoom; F fits; `0` is 100% centred on the selection (card positions never change); N adds; Delete/Backspace opens the delete dialog (always confirmed); Esc closes, then clears; Alt+arrows move a card. Enter acts on the card chosen last (`enterTarget`: a click, a search pick, an arrow key or Tab, recorded at once), never on one focus has not yet left; Enter in the search box picks the result, and only the next Enter explores. Never while typing, never with Ctrl/⌘/Alt beyond those, and Enter/Space/arrows keep their meaning on a focused button. An unavailable action says why. Each node is a focusable button; the drawing is `role="group"`, not an image.
- **Orientation and the view** (`view-memory.ts`, held by `view-memory.test.ts`). Tree (left to right) or outline (top to bottom) is the learner's choice, else the device's by width (`OUTLINE_QUERY`), never the frame's shape, so opening the panel never turns the map. The pan and zoom are remembered in this browser per workspace and explored card, and come back only for the same picture (the same cards drawn); otherwise the map is fitted. Reset layout removes saved card positions (confirmed), the orientation choice and remembered views, and fits.
- The layout (`components/nova/knowledge-map/layout.ts`) is deterministic and has no dependency: the same data draws the same map, in any order the server sends it (notes and saved pages hang by name, never newest first, so editing a note moves nothing). Placement is linear in the number of cards. A run of 8 or more cards with nothing inside them wraps into up to 3 short columns (read down each column, in order), with their lines routed along the gaps (`lanes`), so a branch is never one long column; subjects' trees are packed into columns toward a fixed 16:10 shape instead of one strip. Both are constants, never the window's shape. Do not add a physics library or generate edges with a model.
- **Connecting a card that exists** (the + dialog's "Connect existing"; `map-connect.ts`, pure, held by `map-connect.test.ts` and on Postgres by `nova-map-connect.itest.ts`). Only relationships the data stores, each said as what it is: **moves it** (a subject inside a subject, a topic inside a topic or at the top of a subject (across subjects: two `move_topic` in one batch, history and filed items follow), a task as a step or filed under a subject/topic, a note or saved page filed there) or **a link** (a note's `[[link]]` to a topic; a task waiting for another, either way). There is no topic↔topic or subject↔subject link beside the hierarchy (no table for it), so none is offered. Self, a repeat, and a loop are blocked before saving and refused by the server; the move out of the current parent is said before saving. The card is the same row: nothing is copied. The picker searches the map shown, or everything the learner has on request, with each card's path to tell same names apart.
- **Unlinking one connection** (the Unlink button on each row of the details panel's "Connected to"; `map-disconnect.ts`, pure, held by `map-disconnect.test.ts` and `nova-map-connect.itest.ts`). Takes that line off and deletes no card: a subject inside another stands on its own; a topic inside a topic goes to the top of its subject; a step becomes a task of its own; a task, note or saved page filed under a topic stays under its subject, and one filed under a subject is filed under nothing; a `[[link]]` is taken out of the note's text with its shown words kept (`removeLink` in `map-edit.ts`, read the way `note-links.ts` reads links, code blocks untouched, guarded save); a wait is dropped. A topic always belongs to a subject, so that line is explained, not removed. Each is one request whose reply is checked before the map says it was done.

## Themes

`components/theme/kivo-theme.tsx` and the theme blocks in `app/globals.css`.

- Light, Dark and Match device, chosen in Settings or the sidebar, kept in `localStorage` (`kivo-theme`) and written to `<html data-kivo-theme>` by an inline script in the dashboard layout before first paint.
- **Each theme is one block of tokens scoped to `.kivo-app`**: dark (the landing page's near-black and baltic-sea surfaces, the default) on `.kivo-app`, light (paper) on `html[data-kivo-theme="light"] .kivo-app`. The landing and sign-in pages are outside `.kivo-app` and keep `:root`. The app is written against a dark surface with translucent white (`border-white/8`, `bg-white/5`); in light, `--color-white` becomes ink and the surface tokens become paper, so components need no light-specific classes. Write new UI with the same tokens (`text-foreground/60`, `bg-card`, `border-white/8`) and it works in both. Avoid hard-coded hex colours and `text-white` on a coloured fill.
- **Colour roles**: `action` (teal, the landing page's button colour: `bg-action`, `hover:bg-action-hover`, `text-action-foreground`, `text-action-ink`, `bg-action-soft`) is for the primary action, the current page and focus (`--ring`); `nova` / `nova-ink` (the same teal) is for Nova and for learning and progress. The site has one accent, teal; iris (violet) is no longer used. `BUTTON_PRIMARY` in `components/nova/workspace/ui.tsx` uses `action`.
- **The legibility floor**: inside `.kivo-app`, `text-foreground/40` to `/55` (and the sidebar's `/50`, `/55`) resolve to `--subtle`, a solid colour that passes 4.5:1 in each theme; on paper, `text-keppel-300`/`400` resolve to `--nova-ink`. The rules sit in the utilities layer with `:where()` scope, so `hover:` and other variants still win. For new secondary text prefer `text-subtle` or `/60` and above.
- Page frames, serif page titles and the loading, error, notice and empty states are `components/dashboard/page-states.tsx`; use them rather than a page-local copy.
- `.kivo-dark` puts the dark tokens back for a region that is always dark (the Creature world).
- A custom property that points at another (`--x: var(--background)`) is resolved where it is declared, so it does not follow the theme: use `var(--background)` directly.

## Templates 2.0: the library, workspaces and Create with Nova

Held by `templates-v2.test.ts` and `nova-workspaces.itest.ts`. `/templates` (`components/nova/templates/`), routes `GET`/`POST /api/nova/workspaces`, `DELETE /api/nova/workspaces/[id]`, `POST /api/nova/workspaces/propose`.

- **The library** lists `STUDY_TEMPLATES` under three categories (`CATEGORY_INFO`: College, Professionals, Competitive Exams) and their subcategories; a template may be listed in several (`placements`) and is still one template. "For you" (`recommendedTemplates`, `recommendedCategory` in `product/workspace-routing.ts`) orders by what they said at sign-up; every category stays one tap away. Search is a text match over names, purposes and listings.
- **One plan shape** (`product/workspace-plan.ts`, pure): a template applied to its inputs (`planFromTemplate`, inputs derived by `templateInputs`) and a plan Nova wrote are the same `WorkspacePlan`, checked by `checkWorkspacePlan` when proposed and again on the server before creation (the page may edit it; its copy is never trusted). The check holds the honesty rules: a source reference names a file the learner gave; a web address survives only when the learner wrote it (Nova's are dropped, never shown as checked); content from files and Nova's own are labelled apart in the notes it writes; past dates and over-limit items are dropped and listed in `dropped`, as is anything it moves or renames. Topics are a tree (nested `topics`, flat `parent`, or an older plan's `unit`/`subtopics`); milestones are topics of kind `"milestone"` with their own fields (an older plan's `phases` are read into them). Prerequisites, resources and assumptions stay with the workspace row (`aboutOf`); explanations and sources are on each topic's row (`details`). `PLAN_VERSION` 2; `readStoredPlan` reads any stored plan (drafts, history, workspace rows) into this shape.
- **Creating** (`product/workspaces.ts`, the only reader and writer of `NovaWorkspace`) writes subjects and topics (`declareWorkspaceSubjectsIn` → `declareSubjectsIn`, the one subject writer), dates (`addDatesIn`, exams.ts), tasks (`createTasksIn`, tasks.ts, keyed `ws:<clientKey>:<key>`) and notes (`createNotesIn`, notes.ts) in one transaction with the workspace row: whole or nothing (a task-limit refusal leaves nothing). One creation per `clientKey`. A near-copy (same template or same name) is not made until the learner chooses: add to it (merges: subjects by name, tasks by key, a note is skipped when they have one with that title anywhere; nothing is changed or removed) or create another. Removing a workspace removes its row only.
- **Create with Nova** (`product/workspace-proposal.ts`, `product/workspace-generation.ts`): one fast call reads the request into a `CreationIntent`; code routes it by outcome (`routeRequest`: `not_creation`, `clarify`, `use` a template as it is with no further call, `adapt` a template with Nova, or `custom`), never by shared words; a plan call follows only for `adapt`/`custom`. Files (PDF, PNG, JPEG, WebP; up to 3, 3 MB together, 40 PDF pages; checked by their bytes, locked PDFs refused) are sent to the model as attachments through the one LLM client (`LlmRequest.attachments`: Gemini inline data, OpenAI file/image parts); Kivo has no OCR of its own. Files and request are material, not instructions. Kivo has no web search: every Nova plan says so (`NO_RESEARCH`). Proposing stores nothing. Only bodies that call a model are metered (`metered`) and limited (4 a minute); template previews and creation are not.
- **Chat**: the Understanding Brain's `create_workspace` request action decides `offer_workspace` (code-worded, never the model): both surfaces open a Build with Nova draft from the learner's words (`openDraftFromChat`) and link to `/build?draft=<id>`. Nothing is created from a sentence. (Older links to `/templates?create=` still open Create with Nova.)
- **The library is a shortcut now**, linked from Build with Nova, not in the sidebar (`NOVA_LINKED_ROUTES` in `companion.ts` keeps it a Nova page). "Start from a document" is Create with Nova, the one path that reads files.
- **Schema**: `NovaWorkspace` (additive). `prisma db push` before deploying the API that reads it.

## Build with Nova: a conversation that builds a workspace

Held by `builder.test.ts` and `nova-builder.itest.ts` (web: `plan-edit.test.ts`). `/build` (`components/nova/builder/`), `product/builder.ts` (the only reader and writer of `NovaWorkspaceDraft`), `product/builder-state.ts` (pure rules), `product/builder-conversation.ts` (the reading call), `writeBuilderPlan` in `workspace-generation.ts`, routes `GET`/`POST /api/nova/builder`, `GET`/`PATCH /api/nova/builder/[id]`, `POST …/[id]/messages`, `…/approve`, `…/cancel`, `…/retry`, and `GET /api/nova/workspaces/[id]` (the live workspace). It is the main way in: the sidebar's "Build with Nova", the first-run screen on Today (`NovaOnboarding`, setup form behind "Set it up yourself") and the onboarding finish button all lead here.

- **A draft is a conversation and its proposal, nothing else.** Statuses `discovery → drafting → awaiting_approval → building → ready` (or `failed`, `cancelled`), transitions in `TRANSITIONS`. The learner's subjects, tasks, notes and dates are written only on approval, through `createWorkspace` (so the same writers, one transaction, merges for an existing workspace).
- **Code decides, the model reads and words.** Each learner message is one main-tier call that returns JSON: the reply, `next` (`ask` / `draft` / `revise` / `chat`), the learner's facts each with a quote, Nova's assumptions and suggestions. `readTurn` keeps a fact only when its quote is in what the learner wrote (else it is shown as an assumption); `decideStep` never drafts from no facts, treats `chat` as talk, and with a proposal any change is a revision. There is no question count after which it drafts. What Kivo knows (sign-up answers, goals, subjects, workspaces: `knownFacts`) is given to the model as "do not ask again" and shown as "From your Kivo profile".
- **Understand before proposing.** A first message that gives fewer than `MIN_FACTS_TO_DRAFT` (2) facts is answered with a question even when the model wants to draft (`STARTING_QUESTION`, and the model's "I'll put together…" reply is dropped: `overruled`), except when improving a workspace they have, which is context enough. After one question the model's `draft` is trusted. The conversation prompt names each kind of work's words and what is worth knowing (academic: subjects, topics, revision, exams; project: milestones, tasks, dependencies, releases, never a syllabus; skill: stages, concepts, exercises; work: deliverables, action items), and the plan writer gives a project one subject named after it, whose topics are its parts.
- **The page** (`components/nova/builder/`). `/build` opens straight into the split view: a new conversation with example prompts on the left (an example only fills the message box), the empty playground on the right, templates as a link. The words the playground uses follow `brief.kind` (`builder-view.ts`: `wordsFor`, so a project shows Milestones and Parts, a study plan Phases and Subjects), and each view has a "Change this with Nova" hint (`hintFor`) that puts the start of a sentence in the message box and sends nothing; the live workspace's hint says only what Nova can do there (add). Decisions sit on the playground's bottom bar (`proposal-actions.tsx`): approve (disabled while Nova writes a new version, so the version approved is the one on screen), edit, discuss, Nova's suggestions as refinements, discard, build progress and failure, and the built links. The chat panel holds the conversation only.
- **Nothing is streamed.** The model returns each reply and each version whole, after the server has checked it. The page draws a reply that arrived while it was open word by word (fast, and at once under reduced motion) and a new version item by item, lighting what it changed against the version before (`planDiff`, from the plan as it arrived, so the learner's own later edits are never marked). The activity lines are the job's stage as the server reports it (`reading` / `writing` / `building`) in the kind's words; there is no step the server has not reached.
- **Jobs run after the response.** A message claims the draft's one job (conditional on `updatedAt`, so a second message gets `busy`); the route spends one request of the AI allowance first (`spendForTurn`, 8 a minute), answers, and runs the job with `after()` in the API process, tokens metered. The page polls `GET` for the job's real stage (`reading` / `writing`). A job writes only while the row carries its `jobId` (cancel clears it); a job silent for `PENDING_STALE_MS` (3 min) is stale and may be retried. This keeps 60–90 s plan writes off the web proxy's timeout.
- **Versions.** Every change to the plan, Nova's or the learner's, is a new `version`. The learner's edits (`PATCH`, checked by `checkWorkspacePlan`, links kept only if they wrote them) apply only on the version they were made on (409 `stale` otherwise). Nova's proposal applies only if the plan is still the version the message was sent on; otherwise the learner's edit stays and Nova says so. Each new version's message names what was added and removed (`planChanges`). Approval names a version; only the current one builds, from the server's stored copy, under the key `d-<draft>-v<version>`, so approving twice (or at once) builds once.
- **Something they already have** (`product/builder-changes.ts`, pure; held by `builder-changes.test.ts` and `nova-builder-edit.itest.ts`). A conversation works on an existing resource when it was pointed at one ("Improve with Nova", `targetWorkspaceId`), when it built one and goes on (a `ready` draft takes new messages: `ready → discovery`, its workspace becomes the target), or when the learner names one. Naming: the reading reports `resource: { name, intent: open | change | new }`; code (`decideResource` / `matchResources`: whole words, course code, acronym, "my … plan" wrapping ignored) looks only among *their* workspaces and subjects (`resourceCandidates`). One match is opened (a subject that belongs to exactly one workspace is that workspace; otherwise `targetSubjectIds`); several are offered to choose from (`brief.choices`, buttons that send the name); none is said to be none; `new` opens nothing (and says it will be separate when a match exists). Nothing is resolved from a guess, and the model never names an id.
- **Changes, not a new plan.** With a target, a proposal is a change set (`NovaWorkspaceDraft.changes`): operations on its records by id (`ChangeOp`: add/rename/remove topic, add/remove subject (with its topics and dates, each listed; past dates are kept, unfiled), add/update/remove/order tasks, add/move/remove dates, add/remove notes, `remove_workspace` (everything in it, each listed; finished tasks stay; all or nothing)), written by `writeBuilderChanges` and kept only when `checkChanges` finds the id in this resource and the change valid (no studied topic removed, no finished task deleted, no past day, no repeat, no placeholder topic), each said in words, what is left out listed with why. The page shows the stored records (`DraftView.current`, read through their owners on every view) with the changes marked on them; the learner can leave changes out (`PATCH { keep }`, a new version). Approval runs `changeResource` (workspaces.ts): checked again against the records as they are; a change or removal that no longer fits refuses the whole set (`stale`; Try again re-proposes); otherwise one transaction through each owner (topics via `playStudyEditsIn`, Subject Studio's own batch and lock; tasks via `updateTasksIn` / `removeOpenTasksIn` / `placeTasksIn` / `createTasksIn` keyed by the change set; dates via `addDatesIn` / `updateDatesIn`; notes via `createNotesIn`). Topics have no order column, so milestones are never reordered; their tasks are.
- **It keeps to its job** (held by `builder-changes.test.ts` and `nova-builder-edit.itest.ts`). A message asking for something this page does not do (an essay, code or homework answers, general knowledge unrelated to the plan, reminders, settings, Telegram; never removing or undoing what it works on) is read as `next: "decline"` and answered by code with `DECLINE_REPLY`: nothing is opened, proposed or counted, and a conversation with nothing but declined requests is not listed. A change request names the kinds of record it is about (`touches`: topics, subjects, tasks, dates, notes; stored on the brief); `withinAsk` keeps only operations of those kinds and lists the rest as "not asked for", so "add two topics" never brings tasks, notes or dates. Operations on records outside the resource were already dropped by `checkChanges`. Both prompts also say to add nothing the conversation gives no reason for.
- **After approval** the page opens the Knowledge Map on the subject (`/map?focus=subject:<id>`, `mapDestinations`) once the server answers `ready`; with several subjects the bar offers each instead. A failed build stays on the page.
- **Going back is the history** (`builder-history.ts`, the only reader and writer of `NovaWorkspaceDraftVersion`): every proposal (Nova's, the learner's edits merged while they type, restored ones), every change set, and a snapshot of the records each time something is built or applied. History (on the right) lists them, shows one read-only and restores it as a new version, losing none: before anything is built the plan is the proposal again; once it exists, `changesToReach` works out the change set that brings the records back, checked by `checkChanges` and approved as usual. "Revert the changes" (the reading's `undo`) restores the version built before. Held by `builder-history.test.ts` and `nova-builder-edit.itest.ts`.
- **Deleting what Nova made** (`deletionScope` / `deleteResource` in workspaces.ts, `confirmDeletion` / `keepResource` in builder.ts, `/api/nova/builder/[id]/delete` and `/keep`): a request to delete something whole (the reading's `deleteAll`) is never declined; which one is settled first (asked when a name could be several), then code works out what goes: the tasks the workspace made (clientKey `ws:<key>:`) and their steps, the notes it wrote that nobody has edited, its dates, its unstudied topics, its subjects once nothing else is in them and no other workspace holds them. What Nova adds later is recorded on the workspace's plan (`nova.added`) so it counts as Nova's. A step the learner added under a task that goes is kept as a task of their own. The scope is shown in full; Delete opens a confirmation; the server deletes exactly the scope shown (fingerprint) or nothing.
- **Tasks are trees** (`task-tree.ts`, imported by the web app too): `NovaTask.parentId`, up to `TASK_DEPTH_MAX` (8) levels, no loops, a step filed where its task is, removing a task removes its steps. Plans name a task's `parent` by key; change sets add steps (`parentId` / `parentKey`) and move tasks (`update_task` `parentId`). The playground edits the tree (add step, indent, outdent, fold, waits-for both ways); the Planner shows steps as a checklist in the card; the Knowledge Map shows a topic's tasks in its panel (tasks are never points on the map). A wait across milestones or between steps of one task is dropped by code.
- **Consent to build, and tasks only when asked** (held by `builder.test.ts`, `task-consent.test.ts` and `nova-builder-consent.itest.ts`). A new plan is drafted only with the learner's consent, kept in `brief.consent`: a button they pressed (`action` on their message, honoured only under the Nova message that `offer`ed it: `pressed`), or their own words quoted from their latest message (`build` in the reading). A goal, a shared file, an answer or brainstorming is not consent; when the model would draft without it, code asks `PLAN_QUESTION` (have a plan, or build one?) with its choices. From the learner's `BUILD_OFFER_AFTER` (3) message in the planning conversation (`planningTurns`, counted from the stored messages since the last build), a question carries the "build with current context" shortcut; showing it is not consent. Tasks are written only as `brief.tasks` (`TaskConsent`: none by default, all, or scoped to named subjects, topics or milestones and what is inside them) allows: `filterPlanTasks` on every proposal and `filterTaskOps` on every change set, after the model, whatever it wrote; nothing there removes an existing task. A proposal with no tasks says so and offers them. `placeUnder` puts what a change adds inside the parent the learner named (`brief.under`): a new subject left at the top goes inside that subject, or becomes a topic inside that topic. The playground draws a parent as a container holding its children (`nestRows`), and a live workspace's topics as they will stand once the changes apply (`topicOutline`).
- **Subjects inside subjects** (`NovaSubject.parentId`, onDelete SetNull; held by `subject-groups.test.ts` and `nova-subject-groups.itest.ts`). A subject can sit inside another ("Semester Five" › Automata), up to `SUBJECT_DEPTH_MAX` (4) levels, never in a loop (`canPlace` from `task-tree.ts`, with its own cap). One writer, `placeSubjectIn` in `setup.ts`, reached through Subject Studio's edits (`move_subject`, `add_subject` with `parentId`/`parentName`; the structure version includes placement). Change sets have `move_subject`, `rename_subject` and `add_subject` with `key`/`parentId`/`parentKey`; an `add_subject` whose "topics" name subjects already here moves those subjects into it (seen 26 Oct). Plans name a subject's `parent`; building places only subjects the build creates. History snapshots placement and moves subjects back; removing a group leaves what is inside on its own; a group Nova added counts as Nova's for deletion. The reading's `removes` (did they ask to take anything out): false keeps no removal (`withinAsk`), so "keep everything, just put them under Semester Five" never removes a subject (seen 26 Oct). The map draws a `contains` edge and lays a group's subjects on a ring around it; scoping to a group shows everything inside it; Build with Nova sends the learner to the outermost subject.
- **Priorities are the learner's**: a plan Nova writes stores none (`checkWorkspacePlan` `nova: true`); its view is `suggestedPriority` with a `priorityReason`, accepted or dismissed on the page; the learner's own survive revisions (`keepLearnerPriorities`). In a change set Nova sets one only when the request is about priorities (`touches` has `priorities`; otherwise `withoutPriorities`).
- **What to call them and in which language** (`greetings.ts`, no imports): onboarding's optional first question saves `onboardingAnswers.nickname` (Settings edits it); the Today chat, Telegram, Today's greeting and Build with Nova use it. Today's greeting, Build with Nova's opening and code's own questions are in the language they chose (English, Hindi in Devanagari, Hinglish in Roman letters).
- **Screenshots** paste into the message box (`paste.ts`): attached as "Screenshot N", thumbnails, the same checks as attaching, a big image scaled to 2000 px first.
- **Planning engine (26 Oct; held by `planning-engine.test.ts` and `nova-planning-engine.itest.ts`).** No kind of work rewrites a plan's structure (`projectShape`/`studyShape` are gone): projects may have several workstreams, academic plans units › topics › subtopics, skills ordered stages with their concepts; `kind` sets wording, questions and checks. Depth and detail follow the scope asked (the prompt's rule; "keep it simple" is gone). Only the first version is written whole (`writeBuilderPlan`, JSON output mode, `PLAN_OUTPUT_TOKENS`); every revision is `ChangeOp` operations on the proposal's items (`planDetail` gives them ids, `applyToPlan` plays them, the same `checkChanges`/`withinAsk` as for a workspace), so nothing it doesn't name changes and a plan of any size is revised safely. A reply cut off at its limit is an explicit error (`TRUNCATED`, `TOO_LONG`), never half an object. `plan-feasibility.ts` (pure): errors (work due after its deadline, a task due before what it waits on, a step after its task, broken or circular waits) block approval; warnings (a week over the stated hours, missing estimates, near-duplicates, study topics without practice, a shared syllabus nothing cites) are advice; dates are never moved to fit. At most one suggestion (`SUGGESTIONS_MAX`). A plan or change reply that isn't JSON is asked for once more (`UNREADABLE_TRIES`). A revision that changes nothing is not a new version (`changedNothing`); nesting and order changes count.
- **Deleting a conversation** (`DELETE /api/nova/builder/[id]`, `deleteDraft`) removes the draft row and its files only (not while building). Nothing points from a workspace, subject, task, note or date back to a draft, so what it built stays everywhere.
- **Topics as a tree** (`NovaTopicMastery.parentId`/`position`/`kind`/`details`; rules in `topic-tree.ts`, `TOPIC_DEPTH_MAX` 6). Units, topics and subtopics are rows in saved order (never alphabetical; a row with no position sorts after, by creation). Only a leaf that is not a milestone is studied: `getAllTopicMasteries` (every queue, review, plan and count) filters with `STUDY_TOPIC_WHERE`; a topic that gains topics inside it keeps its row and history and comes back when they go. Writers: `declareTopicTree`, `placeTopicIn`, `orderTopicsIn`, `setTopicDetailsIn`, `moveTopicIn` (with its subtree) in the topic engine, reached through Subject Studio's edits (`add_topics` with a parent, `move_topic` with `parentId`/`index`, `order_topics`, `update_topic`; removing a topic needs what is inside it gone first). A subject still holds a name once at any level; a repeat under another parent is renamed "Name (Parent)" and said. `isPlaceholderTopic` drops placeholders, said in `dropped`. A study plan with no syllabus carries `NO_SYLLABUS`.
- **Waits** (`NovaTaskDependency`, task waits on dependsOn, both cascade): a task may wait on several (`PlanTask.after: string[]`), written by `tasks.ts` only (`addWaitsIn`, `setWaitsIn`; no self-wait, no circle, both tasks the learner's), shown on task items as `after`, drawn on the map as `depends_on` edges. Waits between sibling steps, or on the task a step is part of, are left out and said. A task's `topic` names its topic or milestone.
- **Knowledge Map per workspace**: `loadNovaKnowledgeMap(id, { workspace })` draws one workspace (its subjects and those inside them, its tasks by key, unfiled ones too), the one worked on last by default, `"all"` for everything; the page switches with `?workspace=`. Nodes: subjects, topics (`parentId`, `order`, `kind`, `studied`, `details`), tasks (cards with `step` and `has_task` edges), notes, pages. The layout (`layout.ts`) is an ordered left-to-right tree (an outline in portrait); branches fold; "Focus on this branch" shows its subtree and ancestors. After approval Build with Nova opens `/map?workspace=<id>`.
- **Across channels.** `builderContextLines` (titles only) reaches Nova's chat context under "What they are building in Kivo", which says changes are approved on the web, never from chat. Telegram and the web Nova box open a draft from the learner's words (the same words on the same day open the same draft) and link to it; the page asks Nova to answer it when opened (`resume`).
- **PDFs and photos in the conversation.** A message (or the opening one) may carry files, checked by `checkFiles` (PDF, PNG, JPEG, WebP; 3 per message, 3 MB together, 40 PDF pages, no locked PDFs) and by conversation (`DRAFT_FILES_MAX` 6, `DRAFT_FILE_BYTES_MAX` 12 MB; a repeated name is numbered). They are stored in `NovaWorkspaceDraftFile` in the same transaction as the claim (a refused claim keeps none), sent as attachments with every reading of the conversation (deadline 75 s with files) and to the plan writer, so the learner can ask about them at any point. A fact taken from a file is kept only when it names a file they shared (shown under "From your files"); page references survive only to shared files; a file the plan did not report reading is shown as not read. Files are deleted when the conversation is built or cancelled. Telegram cannot share files into a draft.
- **Schema**: `NovaWorkspaceDraft` (with `targetSubjectIds` and `changes`) and `NovaWorkspaceDraftFile` (additive), and `PlanTask.after`, `PlanTopic.unit` / `subtopics` (inside Json, no column). `prisma db push` before deploying the API.

## Subject Studio: editing subjects and topics

Held by `setup-edit.test.ts`, `study-proposal.test.ts` and `nova-setup-edit.itest.ts`. `product/setup-edit.ts` (+ `.types.ts`), `product/study-proposal.ts` (+ `.types.ts`), `GET`/`POST /api/nova/subjects`, `POST /api/nova/subjects/propose`, UI `components/nova/knowledge/subject-studio.tsx` ("Edit subjects" on Knowledge).

- **The learner edits their own structure**: add a subject or topics, rename, move a topic, remove. A batch (`StudyEdit[]`) applies whole or not at all, in one transaction that first locks the learner's `NovaAcademicProfile` row, and only against the `version` (a hash of ids and names) it was made from; otherwise 409 `stale` with the structure as it stands. Ids are checked against the learner's own structure; nothing from the request names a learner.
- **Writers stay single.** Adding goes through `declareSubjectsIn` in `setup.ts` (the one `novaSubject.create`, shared with `saveSetup`) and `declareTopics`; a topic's row is changed only by the topic engine (`renameTopicIn`, `moveTopicIn`, `removeTopicIn`); subjects by `renameSubjectIn` / `removeSubjectIn` in `setup.ts`. Notes, tasks and saved pages filed under a topic follow it through `refileNotesForTopic`, `refileTasksForTopic` and `refileResourcesForTopic`, each in its owner, in the same transaction. Mastery history is read only through Progress (`topicsWithMasteryHistory`).
- **Renaming or moving keeps the topic's row**, so its mastery, review schedule and history stay. Past sessions keep the topic name they were recorded with. `[[links]]` in note bodies are text and are not rewritten.
- **Nothing studied is removed.** A topic with recorded study (reviews, a study date, mastery history, a session with its id) can be renamed or moved, never removed; archiving needs a column (schema request in `audit/phase2-tracker.md`). A subject is removed only once it has no topics and no dates; its notes, tasks and saved pages stay, unfiled.
- **Archived topics** (`topic-archive.ts`) are listed in Subject Studio marked archived, with Restore. Their names stay taken in their subject (the unique key): adding one restores that row (`declareTopics`), renaming onto one is refused with a pointer to Restore, and a subject with archived topics is not removed. Archiving or restoring changes `version`. Nova's proposal prompt marks them `[archived]`.
- **Ask Nova to update** (`proposeStudyEdits`): one model call given the structure (ids, names, which topics are studied), goals, learning contexts and the request; the model proposes `StudyEdit`s with a reason. Each is played in order through `checkStudyEdits`; what fails is dropped and shown with why. Nothing is stored or applied: the page keeps the draft in `localStorage` (`kivo-study-proposal`), the learner edits names, deselects, and approves through the ordinary `POST /api/nova/subjects` with the proposal's version. Four proposals a minute per learner; 25 s deadline.

## Study setup: one setup, three ways in

`product/setup.ts` is the only reader and writer of a learner's study setup: subjects, topics, exam dates, normal daily minutes and usual study time. The rules, each held by `study-setup.test.ts` or `nova-setup.itest.ts`:

- **Three ways in, one writer.** The setup page (`apps/web/components/nova/setup-form.tsx` → `POST /api/nova/setup`), the web chat and Telegram all end at `saveSetup`. - **Saving merges and never duplicates.** Subjects and topics are matched case-insensitively; exams go through `addExam`, which already refuses a duplicate. A draft with any problem is refused whole.

The older `preferredStudyHoursPerDay` default (3.0) is never read as a stated value.

- **A profile made by setup takes the account's timezone at once** (`ensureLearnerTimezone` in `saveSetup`, only while the profile has none). The device reports its zone before a new learner has a profile, so without this their first plan counted days in UTC.
- **Setup is complete when one subject has one topic.** That sets `onboardingComplete`; year, goals and the rest are not asked. The Planning Engine then has `new_material` blocks to offer at once.

No Response Brain, no canonical turn. The older conversation in `nova/onboarding/` is no longer called by any surface.

## Deadline types and the pace projection

Held by `deadline-types.test.ts`. `product/deadline-types.ts` (pure), `product/pace.ts` (pure).

- **One record, one planner, six kinds.** A dated thing is a `NovaExam` row; `examType` holds its kind: `exam`, `assignment`, `project`, `interview`, `certification`, `other`. No schema change and no second table. Any other stored value (older rows hold `midterm` and the like; the column still defaults to it) reads as `exam` through `deadlineType`, so every existing row behaves as it did.
- **What a kind may do to a day** is `DEADLINE_RULES`: `exam` and `certification` prepare their subject's topics inside the planning window and take the whole day inside three days; `interview` is prepared for but never takes the day; `assignment`, `project` and `other` change no study block. They are dates, shown and counted down, and their steps are the learner's tasks.
- **Where the rule is applied.** Twice, the same way, in `product/planning-inputs.ts` and `nova-orchestrator.ts`: `upcomingExams.filter(takesOverTheDay)` goes to the academic state (so only a test can cause exam crisis), and `upcomingExams.filter(preparesTopics)` goes to `selectActiveExam`. The Planning Engine's exam-prep step follows the active date's own distance (`examContext.daysUntil`), not the academic state's. Do not branch on a kind anywhere else: add a field to `DEADLINE_RULES`.
- **Words.** A block's reason names the kind ("interview in 3 days"). `TodayDeadline` carries `kind` and `kindLabel`. The countdown message is told to use the name on record and not to call a date an exam unless the facts do; its plain line opens "Coming up."
- **Giving a kind.** `addExam` takes `kind` (not `type`: Telegram passes its action object whole, and that object's `type` is `"add_exam"`). The setup draft's `exams[].type` and `PATCH /api/nova/exams/[id] { type }` are validated by `parseDeadlineType`; an unknown kind is refused. A date saved without a name is named for its kind. Telegram still adds exams only.
- **The pace projection is read-only arithmetic** on the Planner's pressure cards (`PlannerPressure.pace`), for a date the planner prepares for whose subject has topics: topics not yet solid at `EXAM_TOPIC_MINUTES` each, against the days left at the usual daily time. It states its assumptions every time (equal topics, every day given to this one subject, a guessed daily figure when none was stated). No engine or decision reads it, and it changes no plan. It is not a forecast and the page says so.

## Calendar and reminders

Held by `calendar-rules.test.ts`, `calendar-grid.test.ts` (web) and `nova-calendar.itest.ts`. `product/calendar.ts` (only reader and writer of `NovaCalendarEvent`), `product/calendar-rules.ts` (pure), `product/calendar.types.ts` (contract, no imports), `proactive/event-reminders.ts`, routes `GET`/`POST /api/nova/calendar`, `PATCH`/`DELETE /api/nova/calendar/[id]`, `POST /api/nova/exams`; UI `/calendar`, `apps/web/components/nova/calendar/`.

- **One calendar over three records.** Events are `NovaCalendarEvent` (classes, meetings, study blocks, personal). Tasks with a due day come from `listTasksDueBetween` in `tasks.ts`, and dated deadlines from `listDeadlinesBetween` in `exams.ts`; neither is copied. From a day the learner adds an event, a task (the board's own `TaskEditor` and route) or a deadline (`addExam`, the one writer, via the new `POST /api/nova/exams`). An event can point at a task (`taskId`, set null if the task is deleted) to set aside time for it.
- **Days and moments.** An all-day event is days only (`startDay`/`endDay`), so it never moves with a timezone. A timed event is given as wall-clock times in its zone and stored as moments (`zonedInstant`, DST-safe: a skipped time lands after the gap, a repeated one is the first); its days are where those moments fall in that zone. Ranges are read by `startDay`/`endDay`, at most 62 days.
- **Ownership** comes from the session cookie (`requireTaskLearner`); every query carries the profile id, and a task or subject an event names is checked to be the learner's own. `clientKey` makes a create idempotent.
- **Reminders** are a fixed list of choices (`TIMED_REMINDERS`, `ALL_DAY_REMINDERS`; an all-day one counts from 09:00 on its day, in its zone). Each write stores `remindAt`. The five-minute tick (`checkin-cron.ts` → `runEventReminders`) claims due ones in the outbox under type `event_reminder` with the key `event:<id>:<remindAt>`, so overlapping ticks send once, and a moved, unreminded or deleted event's old time is never claimed (a claimed-but-unsent one is closed on retry). Failures follow the outbox's retry rules; a blocked chat is marked undeliverable. Later than `REMINDER_GRACE_MINUTES` (30) it is missed, not sent late. The text is written by code, no model.
- **Where reminders go**: the learner's own linked Telegram chat only (`reminderBlock`). No Telegram, or a chat that refuses Nova: nothing is claimed or sent, and the page says so before the learner picks a reminder and shows each reminder's status. Nudges turned off on Telegram do not stop a reminder the learner set. `NOVA_PROACTIVE_DISABLED` stops reminders too.
- **Reminders are not proactive messages**: `loadDelivered` and `recoverPending` skip `event_reminder` rows, so they use none of the daily allowance and are never closed as stale by the proactive tick. Sending one does not set the channel's `lastDeliveredAt` (that also holds the first-use claim).
- **Repeating events** (held by `calendar-repeat.test.ts` and the repeating cases in `nova-calendar.itest.ts`): one row and a rule (`repeat` daily / weekly on `repeatDays` (0 = Sunday) / monthly on the first day's date, optional `repeatUntil`), never a row per date. `occurrencesBetween` (`calendar-rules.ts`, pure) works the dates out for the range asked for, at the same wall-clock time in the event's zone across clock changes; each page item has its own `key` (`<id>@<day>`). A rule an occurrence would overlap the next under is refused (`bad_repeat`). Removing one date adds it to `skipDays` (`DELETE …/[id]?occurrence=YYYY-MM-DD` → `skipOccurrence`, guarded on the list as read); any other change applies to every date. `remindAt` is the next occurrence's reminder (`remindAtFor`): after the tick deals with one (sent, claimed elsewhere, or no channel) it moves on (`moveOn`, guarded on the moment it held), and one the server slept past is moved on as missed, never sent late. A claimed occurrence is retried only while the event as it now is still has a reminder at that moment (`occurrenceOfReminder`), so a changed rule or removed date drops it. The key is still `event:<id>:<moment>`, so each date is sent once.
- **Not built**: reminders on tasks or deadlines (the proactive tick's `task_due` and exam countdown still apply), email or browser-push delivery, and showing events to Nova's planner or prompts. An event is not evidence and changes no plan.
- **Deploy order**: `NovaCalendarEvent` (and its relations) must be pushed (`prisma db push`) before the API that reads it is deployed; the change is additive.

## Daily check-in and proactive timing

Nova has one scheduler path for speaking first: the five-minute tick (`apps/api/lib/internal-checkin-scheduler.ts` → `checkin-cron.ts` → `nova/proactive/nova-proactive-cron.ts`) → `decideProactive` → the outbox (`proactive-outbox.ts`). The daily check-in is a fifth reason in that decision (`daily_checkin`), not a second job. Do not add another timer, queue or outbox for it.

- **What the check-in time means.** `UserProfile.preferredCheckInTime` ("HH:MM", written by Settings → Check-ins via `PATCH /api/settings`; onboarding no longer asks it, and accounts onboarded before 20 October have the time they chose then) is the start of a window of `CHECKIN_WINDOW_MINUTES` (180) in the learner's local day. A tick anywhere inside the window delivers; after it the check-in has expired and is not sent late. It replaces the study-window `daily_nudge` for that learner, needs no plan (with nothing to recommend it asks one question), counts as the day's one push to study, and is skipped when they have studied today or have already written to Nova since the time came round. A time inside quiet hours is honoured because the learner chose it. `UserProfile.nextMessageTime` and `messageSchedule` are legacy fields nothing reads.
- **Where Nova reads account preferences.** `adapters/account-preferences-adapter.ts` only: the check-in time and the browser-reported timezone. `ensureLearnerTimezone` copies a valid account timezone onto `NovaAcademicProfile.timezone` while that is unset; the tick and the Telegram turn both call it, and the dashboard shell reports the device timezone once per visit. A learner with no timezone anywhere is not messaged first and is counted as `no_timezone`.
- **A task due today is a sixth reason** (`task_due`, held by `proactive-grounding.test.ts`). The tick reads the learner's tasks through `listTasks` and passes the open ones whose due day is today (`ProactiveFacts.tasksDueToday`); an overdue task is not a reason again. One message for the first such task and the day (`task:<id>:<day>`), counting the others. It is one of the day's pushes (study window, one push a day, not after they have studied, not through a life constraint) and ranks under a lapse and over a review. Its message names the task and carries no recommended topic and no Start button: a task is the learner's, not a block Nova planned. A task title reaches the wording model as one line of at most 80 characters.
- **`daily_nudge` is kept, as a decision.** It is not a generic nudge: it is a candidate only when the plan has a block for today, it names that block, carries its Start button, goes out at most once a day in the learner's own study window, and is replaced by the check-in for a learner who chose a time.
- **A waiting message whose reason has gone is closed, worded or not.** Before a retry, the tick looks for the message's occurrence among the candidates that hold now. Missing (the exam was moved or removed, the task finished, the day it named over), an unworded claim is closed by `dropUnworded` and a worded one by `dropStale`: its words are no longer true.
- **Observability.** Each tick logs one `{"layer":"nova_proactive","tick":"done", checked, sent, errors, outcomes}` line; `outcomes` counts how each learner ended (`sent`, `send_failed`, `held`, `no_timezone`, `quiet_hours`, `proactive_off`, `undeliverable`, `not_ready`, `nothing_due`, `suppressed`). `GET /api/health` returns the same counts for the last tick plus `startedAt` and `stale`.
- **Hosting.** The tick only runs while the API process is awake. On Render's free plan it sleeps; `.github/workflows/keep-api-awake.yml` is a stopgap, not a guarantee.
- **Tone.** The learner's tone (`product/tone.ts`: gentle, calm, friendly, direct, firm, no-mercy coach; `onboardingAnswers.tone`, read by `loadTone`) reaches wording only, through `chooseRegister` (`decision/register.ts`): one register line each (`no_mercy` is `playful`, the only one that may tease, never insult, humiliate or threaten), `steady` when unset, and `serious` overriding all of them on distress, a hard stretch or an exam within three days. An account with no tone uses its older `UserProfile.accountabilityStyle` ("soft" → gentle, "hard" → no-mercy). The orchestrator, the Telegram first message and the proactive tick all pass it. No decision reads it.
- **Language.** A reply follows the message it answers. Devanagari is decided from the script (`scriptLanguage`, `interaction/language.ts`) with no model; English versus Hinglish is the reading's. Fixed lines have no Devanagari table: Hindi uses the Roman-script Hindi ones.
- **Exam attribution.** Exam prep blocks and the "exam in N days" reason belong to the exam's own subject (`examCoversSubject`, `engines/exam-engine.ts`); an exam with no subject on record covers the syllabus.

## What the record changes in the plan

Learning DNA (`engines/learning-dna-engine.ts`) already grades each conclusion `unknown` / `emerging` / `supported` / `strong` and flags one its latest evidence is pulling away from (`weakening`). A conclusion may change a decision only at `supported` or stronger and not weakening, and only through the engines, never through a prompt. Two do today:

- `usual_study_window` times the study-window nudge (`nova-proactive-cron.ts`), unless the learner chose a check-in time.
- `typical_session` caps block length (`usualSessionMinutes` in `product/planning-inputs.ts` → `PlanOptions.usualSessionMinutes` → `sessionCap` in `engines/planning-engine.ts`). It only shortens, never under `MIN_BLOCK_MINUTES`, and not when the learner said how long they have today.

The other signals (`plan_follow_through`, `days_per_week`, `best_session_size`, `best_study_window`, `revision_spacing`, `needs_more_retrieval`) are shown on the Learning DNA page and reach no decision. Wiring one in means a new `PlanOptions` field or decision fact with the same evidence gate, and a test in `__tests__/learner-adaptation.test.ts`.

## Web and API deploy separately

Vercel deploys `apps/web` on every merge to `main`; Render deploys `apps/api` only on Manual Deploy. A web change that needs a new API behaviour will reach users before the API does. `GET /api/health` reports the API's `commit`. The web app must not treat an unexpected API answer as "signed out": `saveLink` (`components/nova/saved/saved-api.ts`) checks `/api/me` before believing a 401.
